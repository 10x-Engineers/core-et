[[sec-fp]]
== Forward Progress in the Instruction Fetch Path (Draft for Review)

NOTE: This chapter is a rewrite of <<sec-ch3-fe-ic-livelock>> kept alongside it for comparison. Only one of the two will survive.

[[sec-fp-purpose]]
=== Purpose

Sixteen threads fetch instructions through one shared instruction cache. At every point where they meet, one of them proceeds and the others wait. This chapter states what is guaranteed about that waiting, which hardware provides each guarantee, and where a guarantee rests on a heuristic rather than on a bound.

Two distinct properties are at stake, and the hardware that provides them is different:

* *Starvation* is one thread never being served while others are. Arbitration policy prevents it: every arbiter in the path is work-conserving and ages its clients, so no client can be passed over indefinitely.
* *Livelock* is every thread being served and none making progress. Arbitration cannot prevent it, because the threads are being served. A separate mechanism is needed, and the Neighborhood provides one.

The claim this chapter supports is the following. _Under the assumptions of <<sec-fp-assumptions>>, every enabled, unhalted thread eventually receives the instruction block it asked for._ The claim is deliberately weak: it is an eventuality, not a cycle count, because one step in the path has no hardware bound and is closed by a counter instead.

[[sec-fp-why]]
=== Why Forward Progress Is Not Automatic

[[sec-fp-outcomes]]
==== What Happens to a Lookup

A lookup that reaches F2 has five possible outcomes. <<fig-fp-flow>> shows them in the order the hardware evaluates them.

[[fig-fp-flow]]
.Outcomes of a lookup in F2
image::ch03/fig-ll-miss-flow.png["Outcomes of a lookup in F2",width=85%,align=center]

Four of the five leave the thread in a defined, progressing state: it has its block, it has a fault to act on, or a line or a translation has been requested on its behalf and a fill is on its way.

The fifth does not.

[[sec-fp-dropped]]
==== The Dropped Miss

A miss is recorded only if the miss handler is idle when the lookup reaches F2. The condition is explicit in the RTL: `f2_miss` is qualified with `f0_miss_state == Ready`. There is no pending-miss buffer and no retry queue behind it.

A lookup that misses while the handler is busy is therefore *discarded*. The thread is not told. It receives an ordinary miss response, it sets its sleep bit, and it waits for a fill that was never requested for it. It is released by the next fill done, which is a broadcast carrying no address, so it wakes whether or not the fill had anything to do with it.

Three consequences follow, and together they are the whole problem:

. *Each fill-done round services exactly one new miss.* The handler is idle only between a fill completing and the next miss being accepted. Every lookup that arrives later in that round is discarded.
. *A discarded miss costs a full round.* The thread's next opportunity is the next fill done, which is one L1 transaction away, and an L1 miss adds the L2 round trip on top because the L1 is blocking.
. *The thread's arbitration priority does not change.* `f4_update_prio` is asserted only for a hit or a fault, so a thread that only ever misses never moves in the aging matrix.

[[sec-fp-arbiter]]
==== Why the Arbiter Cannot Repair It

The third consequence is worth dwelling on, because it is the reason a separate mechanism exists at all.

The 8:1 LRU arbiter is working correctly throughout. The starving thread is granted in every round and answered in every round. What it is denied is not the port but the *miss handler*, and the arbiter has no visibility of that resource.

Raising the thread's priority would not help either. Priority decides who enters the pipeline first, and the thread that enters first is not necessarily the thread that finds the handler idle: a lookup that hits leaves the handler untouched, so the handler goes to the first *missing* lookup of the round, whoever that is.

Among threads that only miss, the aging matrix is frozen. None of them updates its priority, so their relative order never changes. A thread that starts behind two chronic missers stays behind them for as long as all three keep missing.

In the ordinary case this still resolves. The thread that does take the handler gets its line, retries first in the next round because its priority is unchanged, hits, and only then moves to the back, which lets the next thread through. Eight rounds serve eight threads. That natural bound holds for demand traffic alone, and it is worth stating plainly because it explains why the guard almost never fires.

It fails when a contender takes the handler repeatedly *without ever demoting*. Two such contenders exist: a thread whose fill is discarded before it can use it, which a flush or a cache-bypass configuration can cause, and the code prefetch engine, which is not a thread at all and has no entry in the aging matrix.

[[sec-fp-capture]]
==== Worked Example: the Prefetch Engine Takes the Window

The prefetch engine shares the miss handler with demand fetches and issues in any cycle in which no core presents a request, `f0_prefetch_req_ready = ~f0_req_valid`. The cycles immediately after a fill completes are exactly such cycles: the threads have not been woken yet, so nothing is competing for the pipeline.

<<fig-fp-capture>> follows one round.

[[fig-fp-capture]]
.The prefetch engine takes the miss handler before the woken threads reach F2
image::ch03/td-ll-capture.png["The prefetch engine takes the miss handler before the woken threads reach F2",width=100%,align=center]

[cols="1,6",options="header"]
|===
| Cycle | Event

| 0 | A fill returns. The miss handler leaves `Fill_Wait`.
| 1 | Handler is `Ready`. No core has presented a request, so `f0_prefetch_req_ready` is high and the prefetch request enters the pipeline.
| 2 | Fill done is pulsed to the cores. The prefetch request is in F1.
| 3 | The prefetch lookup reaches F2, is forced to miss, finds the handler idle and *takes it*. The threads have only just woken.
| 4, 5 | The cores present their requests and the 8:1 arbiter grants them. The handler is already busy.
| 7, 8 | The threads' lookups reach F2 and are discarded.
| 9, 10 | Each thread receives a miss response, sleeps, and its miss counter increments. No priority is updated, so the next round starts in exactly the same order.
|===

The engine wins by three cycles, and it wins them before the round starts: it was already in the pipeline when the threads woke. Nothing in the arbitration can recover those cycles, and nothing in the aging matrix records that it happened.

[[sec-fp-mechanisms]]
=== The Mechanisms

[[sec-fp-arbiters]]
==== Bounded Waits at the Arbiters

Three arbiters bound three of the five waits in <<tab-fp-points>>, and all three bounds are structural rather than statistical.

The *core fetch port* uses a 2:1 LRU arbiter whose priority is updated on every grant, so with two clients the grants alternate strictly. A waiting thread is granted after at most one request of its sibling.

The *L0 request port* uses an 8:1 LRU arbiter over an aging matrix with one bit per pair of threads. Because every pair is ordered by exactly one bit, two threads can never hold equal priority and the grant is one-hot, which the RTL asserts. A thread that bids continuously is granted after at most seven grants of other threads.

The *L1 request port* uses a round-robin arbiter between the two micro-caches. The count is one, but the time it stands for is not small: the L1 accepts one transaction at a time and holds its request port closed until that transaction's response, which on an L1 miss means the whole L2 round trip (<<sec-ch3-l1>>). The bound is correct; it is simply expensive.

[[sec-fp-sleep]]
==== Sleep and Wake-Up

A thread that is told to wait must be certain of being woken. Two properties provide that certainty.

*Fill done is a broadcast.* It carries no address and is driven to all eight threads of the micro-cache, so a thread is woken by any fill, not only by its own. A thread whose miss was discarded is therefore released even though nothing was requested for it.

*Fill done is ordered after the last response the fill can affect.* It is driven one pipeline stage later than the response and registered again in the Front End. A lookup that passes the array while the fill is being written still misses, and its miss response is the last one this fill can produce. Sending fill done after that response guarantees every thread has set its sleep bit before its wake-up arrives, so no wake-up can be lost.

The cost of the broadcast is that every fill wakes every sleeping thread, including the ones waiting for a different line. They re-arbitrate, miss again and sleep again. That is wasted L0 bandwidth, and it grows with the number of threads waiting on distinct lines.

A redirect, a thread disable or a halt clears the sleep bit of that thread alone and does so immediately, without waiting for a fill. Fill done remains the only event that wakes all of them.

[[sec-fp-prefetch]]
==== Keeping Prefetch Behind Every Thread

The prefetch engine cannot starve, but it can starve others, so three independent rules hold it below every thread.

. *It issues only in cycles with no core request.* A demand fetch always wins the pipeline over a prefetch in the same cycle.
. *It pauses after a fill it was waiting for.* On fill done it enters `PreReq_Pause` and counts eight cycles with a three-bit counter before it may request again, which is enough for the woken threads to be granted and to reach F2 ahead of it.
. *It is held off after a demand miss has been discarded.* A separate tracker watches for a demand lookup that neither hit nor had its miss accepted. When it sees one it blocks the engine until the next fill done, and then until a core request has entered the micro-cache or sixteen cycles have passed.

Rules 2 and 3 are not redundant. The pause is a fixed eight cycles and a woken thread may have to wait behind up to seven other retries, so its lookup can arrive after the pause has expired; the hold covers that case by waiting for an actual core request rather than a fixed count. Conversely the hold only arms when a miss has already been discarded, so the pause is what prevents the first one.

The scenario of <<sec-fp-capture>> is the gap between them. The pause is entered from `FillDone_Wait`, and an engine sitting in `Request` waiting for an idle cycle never passes through that state, so no pause is started. The hold then ends the sequence after one round, because the discarded miss at cycle 7 arms it.

[[sec-fp-guard]]
==== The Miss-Count Guard

Everything above is a policy. The guard is the backstop that makes the claim of <<sec-fp-purpose>> hold without reference to any policy.

Each thread has a five-bit counter of *consecutive miss responses to its own requests*. It is cleared on a hit, and cleared on any response that reports a fault or an error. The counter advances only when that thread's own response returns, so a thread that is not being granted does not accumulate.

When any counter saturates at 31, a mask removes every other Minion from the arbitration and leaves only the two threads of one Minion bidding: the lowest-numbered Minion that has a saturated thread. Both of its threads are allowed, because a core holds one request at a time and the sibling's request may have to be accepted before the starving thread's can be presented at all.

With every other Minion masked, the starving thread is alone in the idle window, so its miss must be accepted. It then hits, its counter clears, the mask is released, and it passes to the next Minion with a saturated thread if there is one.

<<fig-fp-guard>> shows the sequence.

[[fig-fp-guard]]
.Counter saturation, bid mask and release
image::ch03/td-l0-mask.png["Counter saturation, bid mask and release",width=100%,align=center]

Two design decisions in this mechanism are worth noting, because both are deliberate and neither is obvious.

*The guard masks bids rather than raising priority.* Priority decides who enters the pipeline first, which as <<sec-fp-arbiter>> showed is not the same as who finds the handler idle. Removing the competitors is the only action that makes the outcome certain.

*Every counter is cleared on an error.* A faulting address never hits, so a thread trapped on one would saturate and hold exclusive access that is only ever released by a hit. Clearing the counters lets the fault be taken normally. If the pattern that caused the pressure persists, the counters saturate again and the guard fires again.

[[sec-fp-argument]]
=== The Argument End to End

<<tab-fp-argument>> composes the bounds along one thread's path from wanting an instruction to issuing it.

[[tab-fp-argument]]
.Bound at each step, and what it rests on
[cols="3,3,2",options="header"]
|===
| Step | Bound | Provided by

| Thread to core fetch port | One request of the sibling thread | 2:1 LRU arbiter
| Core to L0 request port | Seven grants of other threads | 8:1 LRU arbiter
| Lookup to miss accepted | *None from arbitration.* At most 31 consecutive miss responses before the thread's Minion is given exclusive access | Miss-count guard
| Miss accepted to fill | One L1 transaction, plus the L2 round trip on an L1 miss | Blocking L1, memory hierarchy
| Fill to wake-up | Same cycle as the fill-done broadcast, which cannot be lost | Fill-done ordering
| Thread to issue | Every other cycle while eligible | Round-robin thread scheduler
|===

Every step except the third has a bound in hardware that holds whatever the other threads are doing. The third step has no such bound, which is the single structural fact worth carrying away from this chapter: *the miss handler is the one shared resource in the fetch path with no arbitration of its own, and the miss-count guard exists precisely to supply what arbitration cannot.*

[[sec-fp-assumptions]]
=== Assumptions

The claim holds under the following conditions. Each is a real obligation on the rest of the system, not a formality.

* Every request to the L1 instruction cache eventually returns a fill, and every translation request eventually completes. Nothing in the fetch path times out or retries on its own.
* Software does not hold a thread in exclusive mode, `WFI` or another architectural stall indefinitely. These stop the affected thread deliberately and are not starvation.
* Faulting fetches are not sustained. Because an error clears every thread's miss counter, a continuous stream of faults from other threads would defer the guard indefinitely. In practice each fault redirects its thread to a trap handler, so the stream does not persist.
* Instruction-cache flushes are not sustained. A flush invalidates a line that is being filled, so a thread can be served and still not hit. The guard gives a thread exclusive access but cannot make a flushed line stay resident.

[[sec-fp-limits]]
=== Known Limitations

These follow from the design. They are not defects, but they bound what may be assumed and they constrain how the interface may be changed.

* *The wake-up is address-less.* Every fill wakes every sleeping thread of the micro-cache, so threads waiting on other lines re-arbitrate, miss and sleep again on every fill. The cost grows with the number of distinct lines being waited on.
* *One outstanding miss per micro-cache.* A miss that arrives while the handler is busy is answered but not recorded, so that thread makes progress only after an unrelated fill wakes it and it retries.
* *Starving Minions are served in a fixed order.* When several Minions have a saturated thread the mask always selects the lowest-numbered one. Each exclusive period ends when its thread hits, so the wait of a higher-numbered Minion is bounded, but the order is not fair.
* *The unattended-miss hold is released by any core request.* Which thread issues it is not checked, so the hold can end before the thread whose miss was discarded has retried. That thread is covered by the guard rather than by the hold.
* *The guard is expensive to reach.* Thirty-one consecutive miss responses, each a full L0 round trip and most of them a full L1 or L2 round trip, elapse before the mask is applied.
* *Prefetching can stall for a long time after a faulting line.* The engine waits for a fill done before moving to the next line, and a faulting line produces no fill of its own. If every thread is hitting, no fill done is generated and the engine stays parked.
