[[sec-ch3-voltage]]
==== Voltage-Domain Crossings

A Neighborhood is divided into two clock and voltage domains:

* *Low-voltage (LV) region*: the eight ET-Minion cores and most of the Neighborhood channel, running on the Neighborhood clock.
* *High-voltage (HV) region*: the logic that interfaces to the Shire Channel, running on the Shire clock.

Blocks were assigned to the two regions for performance and power: the cores and the channel logic run at the lower voltage to save power, while the logic and the memory cells that need speed run at the higher one. Two properties of an SRAM cell decide where its memory has to go, and both improve with voltage:

* *Access time.* A cell driven from a higher supply switches its bit lines faster, so the array is read and written in less time.
* *Noise margin.* Noise margin is the amount of disturbance, from coupling between neighbouring lines, supply droop or process variation, that a cell can absorb before the value it holds or the value being read out flips. It shrinks as the supply falls, so reads and writes become less reliable. A memory macro is therefore characterized with a minimum operating voltage, and carries trim settings, read assist, write assist and write-pulse width, that buy margin back at low voltage at the cost of speed.

Memory cells were kept at the higher voltage for both reasons, which is also why the cells of the crossing FIFOs themselves are always placed in the high-voltage region, whichever direction the interface goes. Margin is not the same as immunity, so the data path from the memory is protected as well: the line returned from the L1 instruction cache data RAM is covered by ECC, the error is reported to the requesting core with the response and it is logged in the Neighborhood ESRs (<<sec-ch3-fe-ic-errors>>).

The two regions are connected by a semi-synchronous interface, and every path between them passes through voltage-crossing FIFOs, whose crossing elements contain the level shifters. The paths that cross are the memory request and response paths, the fast local barrier path, the debug and ESR accesses, and the SRAM interface of the L1 instruction cache, whose data RAM is in the high-voltage region of the Shire Channel. Each crossing costs latency, which is why these paths are longer than their logic alone suggests.

[[sec-ch3-icache]]
=== Neighborhood Instruction Cache

A Neighborhood groups eight ET-Minion cores. Each core has its own private L1 data cache, but none of them has a private instruction cache. Instead, the eight cores share one instruction cache, which is part of the Neighborhood. The cores of a Neighborhood normally execute the same code, so a shared cache holds one copy of it instead of eight, and that saves both area and power.

The shared instruction cache has two levels because of the voltage region its memory has to be built in. SRAM cells are faster and hold their contents more reliably at a higher supply voltage, so the cache data RAM is placed in the high-voltage region, while the Neighborhood itself is low-voltage (<<sec-ch3-voltage>>).

The data RAM is therefore placed outside the Neighborhood, in the Shire Channel, and every access to it crosses the voltage domain, which lengthens the access time. Serving every core from that cache alone would also leave all 16 threads of the Neighborhood, eight cores with two threads each, competing for its single request port. That port is handed out by LRU arbitration, so a thread would wait behind up to 15 others for its turn, even when the line it needs is already present.

To overcome both, the long read latency of a data RAM in another voltage region and the wait for a turn among 16 bidding threads, a micro level was added in front of that cache: two small first-level caches, called L0 micro-caches, inside the Neighborhood, next to the cores. Their data arrays are built in the Neighborhood channel, so a hit is served without crossing into the Shire Channel, and each micro-cache serves half the cores, so eight threads share a port instead of 16.

The shared instruction cache of the Neighborhood is thus split into the following hierarchy:

* *L0 micro-caches*: 16 fully associative lines of 64 bytes each, with their own instruction TLB, PMA check, LRU victim selection and page-table walker port (<<sec-ch3-ptw>>), and a five-stage lookup. There are two of them, called the north and the south micro-cache, serving Minions 0 to 3 and Minions 4 to 7 respectively, that is eight threads each. Both are identical except for one function, the code prefetcher, enabled in the north micro-cache only, for fetching cache lines into the L1 instruction cache.
* *L1 instruction cache*: 32 KB, 128 sets × 4 ways, 64-byte lines, shared by both micro-caches and accessed only when one of them misses. Its tags, LRU and control are inside the Neighborhood; its data RAM is the one in the Shire Channel.

<<fig-ch3-neigh-icache>> shows the structure. <<sec-ch3-icache-rtl>> describes how the two cache levels are packaged in the RTL and what the block connects to. The micro-caches and the L1 instruction cache are described in detail in <<sec-ch3-l0>> and <<sec-ch3-l1>>, and the path from the core's Front End to the cache, with its arbitration and miss handling, in <<sec-ch3-fe-ic>>.

[[sec-ch3-icache-rtl]]
==== Structure and Connections

The cache is implemented in two modules:

* `icache_top` contains both L0 micro-caches and the L1 instruction cache, everything except the L1 data RAM, that is the micro-cache arrays and pipelines, the instruction TLBs, the PMA checks, the L1 tag, LRU and data-array control, and the round-robin arbiter through which the two micro-caches reach the L1.
* `neigh_shared_icache` wraps `icache_top` and adds the Neighborhood-side logic of the core interface, the logic that receives the fetch request of each of the eight cores, holds it per thread and presents one of them to a micro-cache: one request register per thread, the 8:1 LRU arbiter that selects among them, and the per-thread miss counters and bid mask that prevent livelock. These are described in <<sec-ch3-fe-ic>>.

The block connects to five things outside itself:

[cols="2,5",options="header"]
|===
| Interface | Purpose

| Cores | Fetch requests and address-translation configuration, one port per core. Responses and the fill-done indication, one port per L0 micro-cache, each driven to the four cores that micro-cache serves.
| Page-table walkers | Translation requests from the instruction TLB of each micro-cache, one walker per micro-cache.
| Shire Cache | Line requests on an L1 miss, and their responses, over the Neighborhood request and response path.
| L1 data RAM | SRAM read and write requests to the data RAM in the Shire Channel, and the read data returned from it.
| ESR and APB | Configuration (prefetch, bypass, protection and page size), error logging, and debug access to the arrays.
|===

The signals of each interface are listed with the block that uses them: the core-side signals in <<sec-ch3-fe-ic-signals>>, and the rest in the detailed sections of the two cache levels.

[[sec-ch3-fe-ic]]
=== Front End – I-Cache Interface

This section describes the fetch protocol between the ET-Minion cores and the instruction cache, from the Neighborhood side. The core side is described in <<sec-ch2-fe-l0>>.

[[sec-ch3-fe-ic-overview]]
==== Overview

The eight cores of a Neighborhood are served by two L0 micro-caches, each shared by four cores, that is by eight threads. Both L0 micro-caches are backed by the L1 instruction cache of the Neighborhood. <<fig-ch3-fe-ic>> shows the whole path and names the signals of the interface: the two thread buffers and the 2:1 LRU arbiter inside each core, the per-thread request registers and the 8:1 LRU arbiter of each micro-cache, and the round-robin arbiter through which both micro-caches reach the L1 instruction cache.

[[fig-ch3-fe-ic]]
.Front End – I-cache interface
image::ch03/fig-fe-l0-intrf.drawio.png["Front End to I-cache interface",width=100%,align=center]

A fetch request, that is a request from the Front End of a core for the instruction block at a thread's fetch address, travels as follows:

. In the core, the 2:1 LRU arbiter selects one of the two threads, and the selected request is flopped into the F1 request register, which holds it until the Neighborhood accepts it. Each core therefore presents one request at a time.
. In the Neighborhood, the request is steered into the request register of the thread that made it, using the thread identifier it carries. One register exists per thread, so eight per L0 micro-cache, which lets the threads of all four cores arbitrate on equal terms.
. The 8:1 LRU arbiter selects one of the eight captured requests and presents it to the L0 micro-cache. Its grant is returned to the core as the acceptance of the request.
. The L0 micro-cache looks the request up in five stages: arbitration, instruction-TLB translation, tag lookup and PMA check, data-array read, and response.
. One response is returned a fixed four cycles after the grant, for a hit and for a miss alike, and it reaches the core in its F5 stage. It is shared by the eight threads the micro-cache serves and carries no thread identifier; on a hit it carries the instruction block. How a core recognizes its own response is described in <<sec-ch2-fe-track>>.
. On a miss, the L0 micro-cache requests the line from the L1 instruction cache, through a round-robin arbiter that the two micro-caches share. When the fill completes, the micro-cache pulses fill done, which is shared in the same way, and the sleeping threads wake and retry.

[[sec-ch3-fe-ic-arb]]
==== Request Arbitration

This section describes how the Neighborhood decides which thread reaches the L0 micro-cache in a given cycle, and when the arbiter updates the priority that decision is based on. Both start with the registers that hold a request on its way in.

A fetch request is flopped twice before it enters the L0 micro-cache.

*First flop, in the core.* Two threads share one fetch port, so the 2:1 LRU arbiter selects one of them and its request is held in the F1 request register. That register keeps the request until the Neighborhood accepts it, so a core presents one request at a time, carrying the identifier of the thread that made it.

*Second flop, in the Neighborhood.* Each micro-cache is served by four cores, so it sees at most four requests in a cycle, and it holds one request register per thread, eight in all. Each request is written into the register of the thread its identifier names. At most four of the eight registers are valid at a time, because a core frees its F1 register only when its request is accepted. Eight registers exist nevertheless so that every thread bids for itself, which is what makes the arbitration fair between the two threads of a core as well as between cores.

The eight registers bid through the 8:1 LRU arbiter (`arb_lru_delayed_data`). A bid is the register's valid qualified with the thread's bid mask. The mask exists to avoid livelock and is described in <<sec-ch3-fe-ic-livelock>>; until then, take it that masking suppresses a thread's valid at the arbiter, so the thread takes no part in the arbitration while its request stays in its register.

The arbiter is stalled while the micro-cache cannot accept a request, which the micro-cache reports with `f0_req_ready`. Its pipeline never stalls, so this signal is tied high: a request is accepted in every cycle in which at least one thread bids, and the rest of this section takes that for granted.

===== Priority Matrix

The 8:1 LRU arbiter holds its priority in an aging matrix: one bit for every pair of the eight threads it serves, recording which of the two was served more recently. A thread wins when it has priority over every other thread bidding in that cycle, which makes the grant one-hot. Two threads can never hold the same priority, because every pair is ordered by exactly one bit. Granting a thread clears all of its bits, that is it is placed behind every other thread, and the threads that have waited longest move up.

The grant is combinational. In the same cycle it is returned to the core as `icache_req_ready`, the thread's request register is freed, so it reads invalid in the next cycle, and the core may load the request of its other thread into the F1 register. This is why a request is accepted at the earliest in its second F1 cycle.

===== Deferred Priority Update

Every accepted request gets exactly one response, and it comes back a fixed four cycles after the grant, whether it hits or misses (<<sec-ch3-fe-ic-timing>>). The arbiter waits for it: priority is not updated when the grant is issued, but when that response arrives.

Waiting means the arbiter has to remember whose response is due. The grant vector travels down with the request in its own registers, `f1_grant` to `f4_grant`, so that in F4 it can be told which thread the response belongs to (<<tab-ch3-grant-pipe>>).

[[tab-ch3-grant-pipe]]
.Grant pipeline in the Neighborhood
[cols="1,2,4",options="header"]
|===
| Stage | Register | Content

| F1 | `f1_grant` | One-hot grant of the arbiter, loaded in the cycle the L0 micro-cache accepts the request
| F2 | `f2_grant` | Same vector, one cycle later
| F3 | `f3_grant` | Same vector, one cycle later
| F4 | `f4_grant` | Thread whose response is returned in this cycle; selects the priority bits and the miss counter to update
|===

The update is enabled by `f4_update_prio`, asserted when a response is valid in F4 and that response is a hit, or reports a page fault or an access fault:

* *Hit.* Priority is updated and the thread moves behind the others, which gives the waiting threads their turn.
* *Miss.* Priority is left unchanged, so the thread keeps its position while it sleeps and is served early when it retries after the fill (<<fig-ch3-td-l0-miss>>).
* *Page fault or access fault.* Priority is updated, because the thread does not retry the same fetch: the core records the fault with the instruction and takes the trap (<<sec-ch3-fe-ic-errors>>).

Bus and ECC errors do not appear in this condition. Both are reported only with a hit, and a hit already updates the priority.

===== Edge Cases

* *Masked thread.* Masking removes the bid, not the request. When the mask is released the request is still in the register and bids in the next cycle.
* *New request while the register is occupied.* Cores present no second request for a thread that already has one in flight, so the case does not arise. The register ignores it in any event.
* *Reset.* All priority bits start at zero, which orders the threads by index until the first responses have updated the matrix.

[[sec-ch3-fe-ic-timing]]
==== Request and Response Timing

The L0 micro-cache has a five-stage pipeline:

[cols="1,5",options="header"]
|===
| Stage | Operation

| F0 | Arbitration; the granted request enters the pipeline.
| F1 | Instruction-TLB lookup, which translates the virtual address.
| F2 | Tag lookup, PMA check and LRU update; on a miss, the request to the L1 instruction cache is generated.
| F3 | Data array read.
| F4 | Response to the cores.
|===

Every accepted request receives exactly one response from the last stage, for a hit and for a miss alike, so the response arrives a fixed four cycles after the grant. The response is broadcast to the four cores of the L0 micro-cache and carries no thread identifier; each core identifies its own response from the position of its request in time (<<sec-ch2-fe-track>>).

The fill-done signal is driven one stage later than the response, from the stage after F4.

<<fig-ch3-td-l0-hit>> shows a request that hits: the core presents it, the 8:1 LRU arbiter grants it in the next cycle, and the response is returned four cycles later.

[[sec-ch3-fe-ic-miss]]
==== Miss, Sleep and Fill-Done Protocol

A request misses in the L0 micro-cache either because the instruction TLB has no translation for it, or because the line is not in the micro-cache:

* *TLB miss.* A request is sent to the shared page-table walker (<<sec-ch3-ptw>>), and the lookup continues down the pipeline, so the requesting thread receives its miss response with the normal timing.
* *Tag miss.* A request for the line is sent to the L1 instruction cache. The two L0 micro-caches share one request port to the L1 and are selected by a round-robin arbiter, each with a holding register for its request.

In both cases the core that made the request receives a miss response and puts the requesting thread to sleep.

When the fill completes, that is when the translation has been written into the TLB or the line into the micro-cache data array, the L0 micro-cache pulses `icache_fill_done`. The pulse is common to all eight threads it serves and carries no address, so every sleeping thread wakes and retries. A thread whose line is still absent misses again and sleeps until the next fill.

Fill done is deliberately driven one stage later than the response. A request that looks the cache up while the fill is being written still misses, and its miss response is the last one that this fill can cause. Sending fill done after that response guarantees that every thread has entered the sleep state before its wake-up arrives, so no wake-up is lost.

<<fig-ch3-td-l0-miss>> follows one thread through a miss and its retry. The lookup misses in F2, so the miss handler leaves `Ready`, sends the request to the L1 instruction cache in `Request` and waits in `Fill_Wait`. The response in F4 is a miss, the thread sleeps and its priority is left unchanged. When the line arrives the handler returns to `Ready` and fill done is pulsed; the thread wakes, requests again and hits, and only that second response updates the priority.

[[sec-ch3-fe-ic-errors]]
==== Fault and Error Reporting

The response carries the fault and error status of the fetch together with the data:

[cols="2,5",options="header"]
|===
| Field | Meaning

| `page_fault` | The instruction TLB could not translate the address, or the translation forbids the access. Reported whether the lookup hit or missed.
| `access_fault` | The PMA check rejected the physical address. Reported whether the lookup hit or missed.
| `cacheable` | The block comes from a cacheable region, as reported by the PMA check. Valid on a hit.
| `ecc_err` | The line was filled with an ECC error. The micro-cache has no ECC of its own: it stores the error flag that arrived with the fill next to the line and returns it on every hit on that line, until the line is replaced. Only the error classes enabled in the error-log control ESR set the flag. Valid on a hit.
| `bus_err` | The line was returned with an error by the memory hierarchy. Valid on a hit.
|===

A response that reports a fault is delivered like any other response, and the core marks the faulting instruction so that the integer pipeline raises the exception (<<sec-ch2-fe-status>>). Errors detected in the L1 instruction cache data RAM are also logged in the Neighborhood ESRs, which hold a sticky single-bit and double-bit error flag and, for the access that was logged, its way, set and physical address and the ECC blocks of the line in which the error was found.

[[sec-ch3-fe-ic-path]]
==== Complete Path for Four Cores

<<fig-ch3-td-l0-arb>> puts the pieces together: four cores requesting in the same cycle, the two flops each request passes through, the arbitration between the threads, and the five responses. Threads are numbered 2 × Minion + thread, and the LRU order lane lists them highest priority first.

[[fig-ch3-td-l0-arb]]
.Request capture, arbitration and response for four cores
image::ch03/td-l0-arb.png["Request capture, arbitration and response for four cores",width=100%,align=center]

In cycle 0 the four cores present a TH0 request each, and the F1 registers hold them. The thread registers go valid in cycle 1, M0.T0 wins and `icache_req_ready` frees M0's F1 register, which reloads with TH1 in cycle 2. M1.T0 is granted in cycle 2, and in cycle 3 M0.T1 is granted, while M2 and M3 are still holding their first request.

M0 is therefore served twice before M2 and M3 are served once. That is the deferred update at work: M0.T0's grant does not move it behind the others until its response arrives in cycle 5, and until then M0.T1 is the highest-priority bidder. The same property is what lets a thread that missed win its retry immediately, and the miss-count guard bounds how long a thread can be passed over (<<sec-ch3-fe-ic-livelock>>).

The response for M0.T0 appears in F4 in cycle 5, four cycles after its grant, with `f4_grant` naming the thread. It hits, `f4_update_prio` is asserted and the order changes from `01234567` to `12345670`.

[[sec-ch3-fe-ic-livelock]]
==== Livelock and Starvation Avoidance

Up to eight threads share each L0 micro-cache, and the two threads of a core share its fetch port, decoders and issue slot. At every shared point one thread can be delayed by the others. Each shared point therefore has a policy that limits how long a thread can be held back: LRU or round-robin arbitration, a priority rule that favours threads whose requests missed, a wake-up protocol that never loses a wake-up, and a miss-count guard that gives a starving thread exclusive access to the L0 micro-cache. <<tab-ch3-starvation>> lists these mechanisms, and the subsections that follow describe them.

<<fig-ch3-fe-ic-ll>> adds to the interface of <<fig-ch3-fe-ic>> the two blocks that carry the guard: the per-thread miss counters, one set per micro-cache, and the mask they drive, which gates the bids into the 8:1 LRU arbiter.

| Shared resource | Contenders | Mechanism | Guarantee

[[sec-ch3-ll-core-port]]
===== Core Fetch Port

The two thread buffers of a core compete for the core's single request register (`f1_icache_req`) through a 2:1 LRU arbiter (`arb_lru_data` in `frontend_top`). The arbiter updates its priority on every grant, so when both threads request, the grants alternate. The request register accepts a new request only when it is empty or its current request is accepted in the same cycle. Each thread has at most one request in flight. A thread waiting at the core port is therefore granted after at most one request of the other thread has been accepted by the Neighborhood.

[[sec-ch3-ll-arb]]
===== L0 Request Arbitration

In the Neighborhood, each request is captured in a per-thread register and arbitrated against the other seven threads of the same L0 micro-cache by the 8:1 LRU arbiter, which updates its priority with a delay (`arb_lru_delayed_data` in `neigh_shared_icache`). The arbiter keeps a pairwise priority matrix. A granted thread normally moves to lowest priority, but here the update is deferred until the request's response leaves the L0 pipeline. The grant vector is carried from F1 to F4 alongside the request (`f1_grant` to `f4_grant`), and the priority is updated only when the response is a hit or a page or access fault (`f4_update_prio`).

A thread whose request misses therefore keeps its priority (<<fig-ch3-td-l0-prio>>). When it wakes and retries, it wins over any thread that has been served since, so the threads that have waited longest are served first. Only one request per core can be presented at a time, because each core has a single request register, so the arbiter sees at most four active requests in any cycle.

[[sec-ch3-ll-sleep]]
===== Sleep and Wake-Up

Each L0 micro-cache has one miss handler: the logic that handles the L0 micro-cache's single outstanding request to the L1 instruction cache. It consists of:

. a three-state machine (`f0_miss_state`: Ready, Request, Fill_Wait),
. a register holding the physical address of the missing line (`f0_miss_addr`), and
. a flag that marks the miss as a prefetch miss (`f0_miss_is_prefetch`).

A miss is accepted only in the Ready state. The handler then sends the request to the L1 instruction cache (Request state), waits for the line (Fill_Wait state), writes it into the L0 micro-cache unless it is a prefetch, and returns to the Ready state, at which point fill done is generated. A lookup that does not hit returns a miss response to the thread in one of the following three cases:

. The line is not present in the L0 micro-cache and the handler is idle, so the handler accepts the miss and sends it to the L1 instruction cache.
. The line is not present but the handler is busy with another miss, so the miss is not recorded and no request is sent to the L1 instruction cache for it.
. The address misses in the L0 TLB, so a translation is requested from the page-table walker and no request is sent to the L1 instruction cache for it.

In all three cases the thread enters the sleep state (`f0_miss_pending`) and issues no request. The L0 micro-cache pulses `icache_fill_done` to all its threads whenever an L1 fill completes, whether it is a demand miss or a prefetch, and whenever a translation fill completes. On seeing fill done, every sleeping thread wakes and retries according to the arbitration priority. A thread whose line is now present hits, including a thread that missed on the line that was already being filled, and a thread whose line is still absent misses again; if the handler is now idle, its miss is sent to the L1 instruction cache.

A thread sleeps only while a fill is in progress: its own miss, the fill of another thread that kept the handler busy, or a translation fill. Every sleeping thread is woken when fill done arrives. The fill-done timing (<<sec-ch2-fe-miss>>) makes sure that no wake-up is lost: fill done is issued one cycle after the last response the fill can affect, and it is registered again in the Front End. A redirect, a thread disable or a pending halt clears the sleep state of the affected thread only; fill done is the only event that wakes all sleeping threads.

[[sec-ch3-ll-guard]]
===== Miss-Count Livelock Guard

The rules above limit each individual wait, but they do not prevent a thread from missing repeatedly. For example, when many threads miss on different lines and keep competing for the one miss handler, a thread can keep missing and never receive its instructions. The Neighborhood therefore counts, for each thread, the number of consecutive responses to that thread's own requests that were misses (`th_miss_cnt`, 5 bits, saturating at 31). A thread's counter is incremented when its request misses and cleared when it hits. All counters are cleared when any response reports an error (page fault, access fault, bus error or ECC error).

While no counter is saturated, all threads may request access to the cache. When one or more counters saturate, a mask register (`th_miss_mask`) allows only the two threads of one core: the lowest-numbered core that has a saturated thread. Requests from all other threads are blocked. Both threads of the selected core are allowed because the core has a single request register: if it holds the other thread's request, that request must be accepted before the starving thread's request can reach the Neighborhood. The mask is recomputed one cycle after every response.

<<fig-ch3-td-l0-mask>> shows the guard at work: the counter of thread A saturates on its last miss, the mask is recomputed one cycle later and leaves only the threads of that core bidding, so A wins the arbitration as soon as it wakes. Its response is a hit, which clears the counter and releases the mask.

[[fig-ch3-td-l0-mask]]
.Miss-count guard: saturation, bid mask and release
image::ch03/td-l0-mask.png["Miss-count guard: saturation, bid mask and release",width=100%,align=center]

With all other cores masked, only the selected core's misses can reach the miss handler, so the starving thread's line is filled and cannot be displaced before the thread retries. The thread then hits, its counter is cleared, and the mask passes to the next core with a saturated thread, or is removed if there is none.

Clearing every counter on an error avoids a corner case in which a core hangs on a faulting address. A faulting thread never hits on that address, so its counter would saturate and it would keep exclusive access, which is only meant to end on a hit. Clearing the counters and the mask lets the fault be handled normally instead of leaving a mask in place based on stale counts. If the access pattern that caused the livelock persists, the counters saturate again and the guard is triggered again.

[[sec-ch3-ll-prefetch]]
===== Prefetcher Interaction and Retry Windows

The code prefetcher can be started only in the north L0 micro-cache, the one that serves cores 0 to 3: both micro-caches contain the engine, but the prefetch configuration and start registers are connected to that instance alone and tied off in the other. It uses the same miss handler as demand fetches. Three rules keep it below every thread in priority. First, a prefetch request enters the L0 pipeline only in cycles with no core request. The other two rules are timed windows, implemented as two separate state machines in `icache_micro_cache`. They start on different events, end for different reasons and serve different purposes (<<tab-ch3-prefetch-windows>>).

[[tab-ch3-prefetch-windows]]
.Prefetch retry windows
[cols="1,3,3",options="header"]
|===
| | Prefetch pause | Unattended-miss hold

| Where | The prefetcher's own state machine (state PreReq_Pause), a 3-bit counter | A separate tracker (states FillDone_Wait and Req_Wait), a 4-bit counter
| Starts | On a fill done that arrives while the prefetcher is waiting for one (state FillDone_Wait). The fill done can come from the prefetcher's own fill or from a thread's fill. The pause is not started if the prefetcher is in any other state. | Only when a demand lookup misses but is not accepted by the miss handler, normally because it is busy, so a thread is put to sleep without its miss being handled
| Length | Always exactly 8 cycles after fill done | Until fill done, then until the first core request enters the L0 micro-cache, or at most 16 cycles
| Ends | When the counter expires | Usually early, on the first core request or at the 16-cycle timeout
| Purpose | Step back after a fill it was waiting for, most importantly a thread's fill that had blocked it, so that newly woken threads reach the freed handler first | Keep prefetch out while a thread is known to be waiting, until it has retried
|===

*Prefetch pause.* When a fill completes, the miss handler becomes free at the same moment as all sleeping threads wake up. Without the pause, the prefetcher, which issues in any cycle the L0 micro-cache is idle, could take the handler before the waking threads reach the L0 pipeline. The prefetcher waits for a fill done in three cases: when its prefetch lookup found the miss handler busy with a thread's miss, in which case the pause lets that thread and the other woken threads retry first; after its own prefetch fill, when more lines remain; and after a line that faulted. In each case it pauses 8 cycles after fill done before its next request.

The pause is tied to the prefetcher's own state, not to every fill. If a thread's fill completes while the prefetcher is still waiting for an idle cycle to issue its request (state Request), no pause is started. The prefetcher may then issue in an idle cycle between the woken threads' retries and take the freed handler. The unattended-miss hold covers this case only if a thread's miss was turned away while the handler was busy; otherwise the waking threads rely on the livelock guard (<<sec-ch3-ll-guard>>).

*Unattended-miss hold.* A fixed 8 cycles is not always enough: a woken thread may have to wait behind up to seven other retrying threads in the L0 arbiter, so its retry can arrive after the pause has ended. When a demand miss is turned away, new prefetch requests are blocked until the next fill done and then until a core request enters the L0 micro-cache. Without it, a prefetch could take the handler before the retry, and the thread would miss again and sleep for another full fill.

*How the two combine.* A prefetch request is issued only when both windows allow it. If no demand miss was turned away, only the pause applies and prefetching resumes 8 cycles after fill done. If one was, the pause runs first, and if no core request has arrived by then, the prefetch waits until one does or until the 16-cycle limit.

*Limits of the hold.* The hold is released by the first core request from any thread, not necessarily the one whose miss was turned away. It is a heuristic that threads have become active again, not a guarantee for that particular thread; that thread is protected by the livelock guard (<<sec-ch3-ll-guard>>). The 16-cycle limit also protects the prefetcher: if no thread retries, for example because the waiting thread was redirected, disabled or halted, the block would otherwise never clear and prefetching would stop for good. A prefetch fill also generates fill done, so threads that miss while a prefetch holds the handler are woken like any other.

After a prefetch line faults, the prefetcher waits for a fill done before moving to the next line, but a faulting line does not generate a fill of its own. Prefetching then resumes only after some thread's miss causes a fill. If all threads are hitting, this can take a long time.

[[sec-ch3-ll-l1]]
===== L1 I-Cache Miss Port

The two L0 micro-caches of a Neighborhood each hold their single outstanding miss request in a staging register and share the L1 instruction cache through a round-robin arbiter (`arb_rr_data` in `icache_top`). At this level the requesters are the L0 micro-caches, not threads: each staged request is the one miss that the L0 micro-cache's miss handler accepted from one of its threads. When both L0 micro-caches have a request staged, the arbiter alternates, so a miss request waits for at most one miss request of the other L0 micro-cache before it is sent to the L1 instruction cache.

[[sec-ch3-ll-issue]]
===== Decode and Issue

Inside the core, the two threads share the decoders and the issue slot into ID. When both threads have an instruction ready to decode, the decode selection picks the thread that is not presented to ID in the current cycle. The thread scheduler selects between eligible threads in round-robin order and updates its last selection only when at least one thread is eligible. Each thread has its own instruction FIFO and its own stall input (`id_core_stall`), so a stalled thread does not block the other. A halted thread generates its placeholder instruction without bidding for the fetch port. An eligible thread is therefore presented to ID at least every other cycle.

[[sec-ch3-ll-assumptions]]
===== Assumptions

These mechanisms guarantee forward progress in the fetch path under the following conditions:

* Every L1 miss request eventually returns a fill, and every translation request eventually completes.
* Software does not keep a thread's exclusive mode, `WFI` or other architectural stalls asserted indefinitely. These deliberately stop the affected thread and are not starvation.
* Error responses are not sustained. Because an error clears every thread's miss counter, a continuous stream of faulting fetches from other threads would defer the livelock guard. In practice each fault redirects the faulting thread to its trap handler, so such a stream does not persist.
* When several cores have saturated counters, they are served in fixed order, lowest-numbered core first. The waiting time of a higher-numbered core is bounded, because each exclusive period ends when the selected thread hits.

[[sec-ch3-fe-ic-limits]]
==== Known Limitations

The properties below follow from the design of the interface. They are not defects, but they constrain how the interface may be changed and how it behaves under load.

* *Response carries no thread identifier.* A core matches a response to its request by counting cycles, so the fixed response latency is part of the interface contract. A change to the depth of the L0 pipeline has to be matched in the Front End.
* *Fill done carries no address.* Every fill wakes every sleeping thread of the micro-cache. Threads waiting for a different line arbitrate, miss again and sleep again, which costs L0 bandwidth on every fill and grows with the number of threads waiting on different lines.
* *One outstanding miss per L0 micro-cache.* A miss that arrives while the miss handler is busy is answered with a miss response but is not recorded, so its line is not requested. That thread makes progress only after an unrelated fill wakes it and it retries.
* *Starving cores are served in a fixed order.* When several cores have a saturated thread, the mask always selects the lowest-numbered one first. Its waiting time is bounded, because each exclusive period ends when the selected thread hits, but the order is not fair.
* *Unattended-miss hold is released by any core request.* Which thread issues that request is not checked, so the hold can end before the thread whose miss was turned away has retried. That thread is covered by the miss-count guard rather than by the hold.
* *Prefetching can pause for a long time after a faulting line.* The prefetcher waits for a fill done before it moves to the next line, and a faulting line produces no fill of its own. If every thread is hitting, no fill done is generated and prefetching stays paused.
