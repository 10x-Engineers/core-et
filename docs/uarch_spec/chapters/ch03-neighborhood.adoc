[[sec-ch3-voltage]]
==== Voltage-Domain Crossings

A Neighborhood is divided into two clock and voltage domains:

* *Low-voltage (LV) region*: the eight ET-Minion cores and most of the Neighborhood channel, running on the Neighborhood clock.
* *High-voltage (HV) region*: the logic that interfaces to the Shire Channel, running on the Shire clock.

Blocks were assigned to the two regions for performance and power: the cores and the channel logic run at the lower voltage to save power, while the logic and the memory cells that need speed run at the higher one. Two properties of an SRAM cell decide where its memory has to go, and both improve with voltage:

* *Access time.* A cell driven from a higher supply switches its bit lines faster, so the array is read and written in less time.
* *Noise margin.* Noise margin is the amount of disturbance, from coupling between neighbouring lines, supply droop or process variation, that a cell can absorb before the value it holds or the value being read out flips. It shrinks as the supply falls, so reads and writes become less reliable. A memory macro is therefore characterized with a minimum operating voltage, and carries trim settings, read assist, write assist and write-pulse width, that buy margin back at low voltage at the cost of speed.

Memory cells were kept at the higher voltage for both reasons, which is also why the cells of the crossing FIFOs themselves are always placed in the high-voltage region, whichever direction the interface goes. Margin is not the same as immunity, so the data path from the memory is protected as well: the line returned from the L1 instruction cache data RAM is covered by ECC, the error is reported to the requesting core with the response and it is logged in the Neighborhood ESRs (<<sec-ch3-fe-ic-errors>>).

The two regions are connected by a semi-synchronous interface, and every path between them passes through voltage-crossing FIFOs, whose crossing elements contain the level shifters. The paths that cross are the memory request and response paths, the fast local barrier path, the debug and ESR accesses, and the SRAM interface of the L1 instruction cache, whose data RAM is in the high-voltage region of the Shire Channel. Each crossing costs latency, which is why these paths are longer than their logic alone suggests.

[[sec-ch3-icache]]
=== Neighborhood Instruction Cache

A Neighborhood groups eight ET-Minion cores. Each core has its own private L1 data cache, but none of them has a private instruction cache. Instead, the eight cores share one instruction cache, a 32 KB L1 I-Cache that the Neighborhood adds as a shared resource. The cores of a Neighborhood normally execute the same code, so a shared cache holds one copy of it instead of eight, and that saves both area and power.

The shared instruction cache has two levels of access because of the voltage region its memory has to be built in. SRAM cells are faster and hold their contents more reliably at a higher supply voltage, so the cache's data RAM is placed in the high-voltage region, while the Neighborhood itself operates at low voltage (<<sec-ch3-voltage>>).

The cache's data RAM is therefore placed outside the Neighborhood, in the Shire Channel, and every access to it passes through the voltage-domain crossing, which lengthens the access time. Serving every core from that cache alone would also leave all 16 threads of the Neighborhood, eight cores with two threads each, competing for its single request port. Access to that shared port is handled by LRU arbitration, so a thread would wait behind up to 15 others for its turn, even when the line it needs is already present.

To overcome both, the long read latency of its data RAM in another voltage region and the wait for a turn among 16 bidding threads, a micro level was added in front of that shared cache: two small first-level caches, called L0 micro-caches, inside the Neighborhood, next to the cores. Their data arrays are built in the Neighborhood channel, so a hit is served without crossing into the Shire Channel, and each micro-cache serves half the cores, so eight threads share a port instead of 16.

The shared instruction cache of the Neighborhood is thus split into the following hierarchy:

* *L0 micro-caches*: 16 fully associative lines of 64 bytes each, with their own instruction TLB, PMA check, LRU victim selection and page-table walker port (<<sec-ch3-ptw>>), and a five-stage lookup. There are two of them, called the north and the south micro-cache, serving Minions 0 to 3 and Minions 4 to 7 respectively, that is eight threads each. Both are identical except for one function, the code prefetcher, enabled in the north micro-cache only, for fetching cache lines into the L1 instruction cache.
* *L1 instruction cache*: 32 KB, 128 sets x 4 ways, 64-byte lines, shared by both micro-caches and accessed only when one of them misses. Its tags, LRU and control are inside the Neighborhood; its data RAM is the one in the Shire Channel.

<<fig-ch3-neigh-icache>> shows the structure. <<sec-ch3-icache-rtl>> describes how the two cache levels are packaged in the RTL and what blocks they connect to. The micro-caches and the L1 instruction cache are described in detail in <<sec-ch3-l0>> and <<sec-ch3-l1>>, and the path from the core's Front End to the cache, with its arbitration and priority updates, in <<sec-ch3-fe-ic>>.

[[sec-ch3-icache-rtl]]
==== Structure and Connections

The cache is implemented in two modules:

* `icache_top` contains both L0 micro-caches and the L1 instruction cache, everything except the L1 data RAM, that is the micro-cache arrays and pipelines, the instruction TLBs, the PMA checks, the L1 tag, LRU and data-array control, and the round-robin arbiter through which the two micro-caches reach the L1.
* `neigh_shared_icache` wraps `icache_top` and adds the Neighborhood-side logic of the core interface, the logic that receives the fetch request of each of the eight cores, holds it per thread and presents one of them to a micro-cache: one request register per thread, the 8:1 LRU arbiter that selects among them, and the per-thread miss counters and bid mask that prevent livelock. These are described in <<sec-ch3-fe-ic>>.

The top-level `neigh_shared_icache` block connects to five things outside itself:

[cols="2,5",options="header"]
|===
| Interface | Purpose

| Cores | Fetch requests and address-translation configuration, one port per core. Responses and the fill-done indication, one port per L0 micro-cache, each driven to the four cores that micro-cache serves.
| Page-table walkers | Translation requests from the instruction TLB of each micro-cache, one walker per micro-cache.
| Shire Cache | Line requests on an L1 miss, and their responses, over the Neighborhood request and response path.
| L1 data RAM | SRAM read and write requests to the data RAM in the Shire Channel, and the read data returned from it.
| ESR and APB | Configuration (prefetch, bypass, protection and page size), error logging, and debug access to the arrays.
|===

The signals of each interface are listed with the block that uses them: the core-side signals in <<sec-ch3-fe-ic-signals>>, and the rest in the detailed sections of the two cache levels.

[[sec-ch3-fe-ic]]
=== Front End – I-Cache Interface

This section describes the fetch protocol between the ET-Minion cores and the instruction cache, from the Neighborhood side. The core side is described in <<sec-ch2-fe-l0>>.

[[sec-ch3-fe-ic-overview]]
==== Overview

The eight cores of a Neighborhood are served by two L0 micro-caches, each shared by four cores, that is by eight threads, two threads per core. Both L0 micro-caches are backed by the L1 instruction cache of the Neighborhood. <<fig-ch3-fe-ic>> shows the whole fetch path and names the signals of the interface: the two thread buffers and the 2:1 LRU arbiter inside each core, the per-thread request registers and the 8:1 LRU arbiter of each micro-cache, and the round-robin arbiter through which both micro-caches reach the L1 instruction cache.

[[fig-ch3-fe-ic]]
.Front End – I-cache interface
image::ch03/fig-fe-l0-intrf.drawio.png["Front End to I-cache interface",width=100%,align=center]

A fetch request, that is a request from the Front End of a core for the instruction block at a thread's fetch address, travels as follows:

. In the core, the 2:1 LRU arbiter selects one of the two threads, and the selected request is flopped into the Front End's F1 request register, which holds it until the Neighborhood accepts it. Each core therefore presents one request at a time.
. In the Neighborhood, the request is steered into the request register of the thread that made it, using the thread identifier it carries. One register exists per thread, so eight per L0 micro-cache, which lets the threads of all four cores arbitrate on equal terms.
. The 8:1 LRU arbiter selects one of the eight captured thread requests and presents it to the L0 micro-cache. The grant is returned to the core in the same cycle, as `icache_req_ready`, and it frees the core's F1 request register: the core's 2:1 arbiter runs in that same cycle and loads the other thread's request, so the core presents it on the next cycle with no idle cycle in between.
. The L0 micro-cache looks the request up in five stages: arbitration, instruction-TLB translation, tag lookup and PMA check, data-array read, and response.
. One response is returned a fixed four cycles after the grant, for a hit and for a miss alike, and it reaches the core in its F5 stage. It is shared by the eight threads the micro-cache serves and carries no thread identifier; on a hit it carries the instruction block. How a core recognizes its own response is described in <<sec-ch2-fe-track>>.
. On a miss, which can be a TLB miss or a line miss, the L0 micro-cache requests a translation from its page-table walker, or requests the line from the L1 instruction cache through a round-robin arbiter that the two micro-caches share. When the fill completes, the micro-cache pulses fill done to all the threads it serves, and the sleeping ones wake and retry.

The fetch response ports are the exception to that one-core view. The Neighborhood drives one set of them per L0 micro-cache, common to the four cores it serves, so `icache_resp_valid`, `icache_resp_miss`, `icache_resp` and `icache_fill_done` reach all four at the same time. Being common, the response carries no thread identifier and nothing that says which core it belongs to. Each core works that out on its own: it tracks its outstanding request down the pipeline, so it knows in which cycle its response is due and which of its two threads made it, and it ignores the responses of the other three cores (<<sec-ch2-fe-track>>).

[[sec-ch3-fe-ic-arb]]
==== Request Arbitration

This section describes how the Neighborhood decides which thread's request reaches the L0 micro-cache in a given cycle, and when the arbiter updates the priority that decision is based on. Lets start with the registers that hold a thread's request on its way in.

A fetch request is flopped twice before it enters the L0 micro-cache.

*First flop, in the core.* Two threads share one fetch port of the core, so the 2:1 LRU arbiter selects one of them and its request is held in the Front End's F1 request register. That register keeps the request until the Neighborhood (the L0 micro-cache in this case) accepts it, so a core presents one request at a time, carrying the identifier of the thread that made it.

*Second flop, in the Neighborhood.* Each micro-cache serves four cores, so it sees at most four requests in a cycle, and it holds one request register per thread, eight in all. Each request is written into the register of the thread its identifier names. At most four of the eight registers are valid at a time, because a core frees its F1 register only when its request is accepted. Eight registers exist nevertheless so that every thread bids for itself, which is what makes the arbitration fair between the two threads of a core as well as between cores.

The eight registers bid through the 8:1 LRU arbiter (`arb_lru_delayed_data`). A bid is the register's valid qualified with the thread's bid mask. The mask exists to avoid livelock and is described in <<sec-ch3-fe-ic-livelock>>; until then, take it that masking suppresses a thread's valid at the arbiter, so the thread takes no part in the arbitration while its request stays in its register.

The arbiter is stalled while the micro-cache cannot accept a request, which the micro-cache reports with `f0_req_ready`. Its pipeline never stalls, so this signal is tied high: a request is accepted in every cycle in which at least one thread bids, and the rest of this section takes that for granted.

===== Priority Matrix

The 8:1 LRU arbiter holds its priority in an aging matrix: one bit for every pair of the eight threads it serves, recording which of the two was served more recently. A thread wins when it has priority over every other thread bidding in that cycle, which makes the grant one-hot. Two threads can never hold the same priority, because every pair is ordered by exactly one bit. Granting a thread clears all of its bits, that is it is placed behind every other thread, and the threads with the longest wait move up.

The grant is combinational. In the same cycle it is returned to the core as `icache_req_ready`, the thread's request register is freed, so it reads invalid in the next cycle, and the core may load the request of its other thread into the F1 register. A request is therefore accepted at the earliest in its second cycle in the Front End's F1 stage, because that register has to hold it for one more cycle while it is flopped into the Neighborhood's per-thread register.

===== Deferred Priority Update

Every accepted request gets exactly one response, and it comes back a fixed four cycles after the grant, whether it hits or misses (<<sec-ch3-fe-ic-timing>>). The arbiter waits for it: priority is not updated when the grant is issued, but when that response arrives.

Waiting means the arbiter has to remember whose response is due, because the response is shared and carries no thread identifier. The grant vector therefore travels down with the request in its own registers, `f1_grant` to `f4_grant`, so that in F4 it can be told which thread the response belongs to (<<tab-ch3-grant-pipe>>).

[[tab-ch3-grant-pipe]]
.Grant pipeline in the Neighborhood
[cols="1,2,4",options="header"]
|===
| Stage | Register | Content

| F1 | `f1_grant` | One-hot grant of the arbiter, loaded in the cycle the L0 micro-cache accepts the request
| F2 | `f2_grant` | Same vector, one cycle later
| F3 | `f3_grant` | Same vector, one cycle later
| F4 | `f4_grant` | Thread whose response is returned in this cycle; selects the priority bits and the miss counter to update
|===

The update is enabled by `f4_update_prio`, asserted when a response is valid in F4 and that response is a hit, or reports a page fault or an access fault:

* *Hit.* Priority is updated and the thread moves behind the others, which gives the waiting threads their turn.
* *Miss.* Priority is left unchanged, so the thread keeps its position while it sleeps and is served early when it retries after the fill (<<fig-ch3-td-l0-miss>>).
* *Page fault or access fault.* Priority is updated, because the thread does not retry the same fetch: the core records the fault with the instruction and takes the trap (<<sec-ch3-fe-ic-errors>>).

Bus and ECC errors do not appear in this condition. Both are reported only with a hit, and a hit already updates the priority.

[[sec-ch3-fe-ic-timing]]
==== Request and Response Timing

The L0 micro-cache looks a request up in five stages and drives fill done one stage later (<<tab-ch3-l0-stages>>).

[[tab-ch3-l0-stages]]
.L0 micro-cache pipeline stages
[cols="1,5",options="header"]
|===
| Stage | Operation

| F0 | Arbitration; the granted request enters the pipeline.
| F1 | Instruction-TLB lookup, which translates the virtual address.
| F2 | Tag lookup, PMA check and LRU update. A miss is detected here, and accepted if the miss handler is idle.
| F3 | Data array read. On an accepted miss, the request to the L1 instruction cache is driven in this cycle.
| F4 | Response to the cores (`f4_resp_valid`, `f4_resp_miss`, `f4_resp`).
| F5 | Fill-done pulse to the cores (`f5_resp_fill_done`), one stage after the response. Not part of the lookup: it reports that a line or translation fill is complete.
|===

These stages are the micro-cache's own, and they are numbered independently of the Front End's F0 to F7: the F1 request register of the core and the F1 stage of the micro-cache are different things.

Every accepted request receives exactly one response from the last stage, for a hit and for a miss alike, so the response arrives a fixed four cycles after the grant. The response is broadcast to the four cores of the L0 micro-cache and carries no thread identifier; each core identifies its own response from the position of its request in time (<<sec-ch2-fe-track>>).

The fill-done signal is driven one stage later than the response, from the stage after F4.

In the waveforms that follow, a thread is written M0, TH0, meaning thread 0 of Minion 0. <<fig-ch3-td-l0-hit>> shows a request that hits: the core presents it, the 8:1 LRU arbiter grants it in cycle 1, and the response is returned in cycle 5, four cycles later. The grant frees both registers that hold the request, the core's F1 request register and the Neighborhood's per-thread register, which is why both valids fall in the next cycle. `f4_grant` still names M0, TH0, the thread that was granted four cycles earlier, which is how F4 knows whose priority to update: the response is a hit, so `f4_update_prio` is asserted and M0, TH0 moves behind the other threads in the LRU order.

[[sec-ch3-fe-ic-miss]]
==== Miss, Sleep and Fill-Done Protocol

A request misses in the L0 micro-cache either because the instruction TLB has no translation for it, or because the line is not in the micro-cache:

* *TLB miss.* A request is sent to the shared page-table walker (<<sec-ch3-ptw>>), and the lookup continues down the pipeline, so the requesting thread receives its miss response with the normal timing.
* *Tag miss.* A request for the line is sent to the L1 instruction cache. The two L0 micro-caches share one request port to the L1 and are selected by a round-robin arbiter, each with a holding register for its request.

In both cases the core that made the request receives a miss response and puts the requesting thread to sleep.

When the fill completes, that is, when the translation is in the TLB or the line is in the micro-cache data array, the L0 micro-cache pulses `icache_fill_done`. The pulse is common to all eight threads it serves and carries no address, so every sleeping thread wakes and retries. A thread whose line is still absent misses again and sleeps until the next fill.

Fill done is deliberately driven one stage later than the response. A lookup that reaches F2 in the cycle the fill is written hits, because the micro-tag array checks the tag being written as well as the tags it already holds. The last lookup that misses on the line is the one in F3 while the line is written, so its miss response is returned two cycles before `f5_resp_fill_done`. Every thread has therefore entered the sleep state before its wake-up arrives, and no wake-up is lost.

Each L0 micro-cache has one miss handler, which holds one miss at a time; it is described in <<sec-ch3-ll-mh>>. <<fig-ch3-td-l0-miss>> follows one thread through a miss and its retry. The lookup misses in F2, the handler leaves `Ready`, and the request to the L1 instruction cache is driven in F3. The response in F4 is a miss, so the thread sleeps and its priority is left unchanged; the grant has already freed both the core's F1 request register and the Neighborhood's per-thread register.

The break in the waveform stands for the access time of the L1 instruction cache, and of the Shire Cache behind it if the L1 misses as well. That time is not fixed and is far longer than the rest of the sequence. The handler stays in `Fill_Wait` for all of it, so every other lookup that misses meanwhile is turned away, and the core leaves the thread asleep and issues nothing for it. When the line arrives the handler returns to `Ready` and fill done is pulsed; the thread wakes, requests again and hits, and only that second response updates the priority.

[[sec-ch3-fe-ic-errors]]
==== Fault and Error Reporting

The response carries the fault and error status of the fetch together with the data:

[cols="2,5",options="header"]
|===
| Field | Meaning

| `page_fault` | The instruction TLB could not translate the address, or the translation forbids the access. Reported whether the lookup hit or missed.
| `access_fault` | The PMA check rejected the physical address. Reported whether the lookup hit or missed.
| `cacheable` | The block comes from a cacheable region, as reported by the PMA check. Valid on a hit.
| `ecc_err` | The line was filled with an ECC error. The micro-cache has no ECC of its own: it stores the error flag that arrived with the fill next to the line and returns it on every hit on that line, until the line is replaced. Only the error classes enabled in the error-log control ESR set the flag. Valid on a hit.
| `bus_err` | The line was returned with an error by the memory hierarchy. Valid on a hit.
|===

A response that reports a fault is delivered like any other response, and the core marks the faulting instruction so that the integer pipeline raises the exception (<<sec-ch2-fe-status>>). Errors detected in the L1 instruction cache data RAM are also logged in the Neighborhood ESRs, which hold a sticky single-bit and double-bit error flag and, for the access that was logged, its way, set and physical address and the ECC blocks of the line in which the error was found.

[[sec-ch3-fe-ic-path]]
==== Complete Path for Four Cores

<<fig-ch3-td-l0-arb>> puts the pieces together: four cores requesting in the same cycle, the two flops each request passes through, the arbitration between the threads, and the five responses, one for each of the five threads that were granted. In the `LRU order` lane alone the threads are written as digits, numbered 2 × Minion + thread, because eight names do not fit in one cycle; the lane lists them highest priority first.

[[fig-ch3-td-l0-arb]]
.Request capture, arbitration and response for four cores
image::ch03/td-l0-arb.png["Request capture, arbitration and response for four cores",width=100%,align=center]

In cycle 0 the four cores present a TH0 request each, and the F1 registers hold them. The thread registers go valid in cycle 1, M0, TH0 wins and `icache_req_ready` frees M0's F1 register, which reloads with TH1 in cycle 2. M1, TH0 is granted in cycle 2, and in cycle 3 M0, TH1 is granted, while M2 and M3 are still holding their first request.

M0 is therefore served twice before M2 and M3 are served once, and the reason is that the aging matrix has one entry per thread, not one per Minion. Granting M0, TH0 demotes M0, TH0 and nothing else, so M0, TH1 keeps a position that is still ahead of M2 and M3 and wins the arbitration in cycle 3. The deferred update does not cause this: if the priority update occurs at the grant instead of at the response, M0, TH1 still wins in cycle 3.

Per-thread entries are what make the arbitration fair, because the two threads of a core succeed and fail independently. One may hit while the other misses, and a single entry shared by both would demote the thread that missed every time its sibling was served, costing it the position it needs to win its retry after the fill. What the deferred update adds is the next step: a thread whose own response is a miss keeps its place, so it wins its retry immediately, and the miss-count guard bounds how long any thread can be passed over (<<sec-ch3-fe-ic-livelock>>).

The response for M0, TH0 appears in F4 in cycle 5, four cycles after its grant, with `f4_grant` naming the thread. It hits, `f4_update_prio` is asserted and the order changes from `01234567` to `12345670`.

[[sec-ch3-fe-ic-livelock]]
==== Livelock and Starvation Avoidance

Up to eight threads share each L0 micro-cache, and the two threads of a core share its fetch port, decoders and issue slot. At every shared point one thread can be delayed by the others. Each shared point therefore has a policy that limits how long a thread can be held back: LRU or round-robin arbitration, a priority rule that favours threads whose requests missed, a wake-up protocol that never loses a wake-up, and a miss-count guard that gives a starving thread exclusive access to the L0 micro-cache. <<tab-ch3-starvation>> lists these mechanisms, and the subsections that follow describe them.

<<fig-ch3-fe-ic-ll>> adds to the interface of <<fig-ch3-fe-ic>> the two blocks that carry the guard: the per-thread miss counters, one set per micro-cache, and the mask they drive, which gates the bids into the 8:1 LRU arbiter.

.Miss counters and bid mask in the fetch path

[[tab-ch3-starvation]]
.Starvation avoidance mechanisms in the instruction fetch path
[cols="2,2,3,3",options="header"]
|===
| Shared resource | Contenders | Mechanism | Guarantee

| Core fetch port (F1 request register) | 2 threads of a core | 2:1 LRU arbiter, priority updated on every grant | A waiting thread is granted after at most one request of the other thread
| L0 request arbiter | 8 threads of 4 cores | 8:1 LRU arbiter whose priority is updated only on a hit or a fault | A thread whose request missed keeps its priority for its retry
| L0 miss handler | 8 threads and the prefetcher | Fill-done broadcast with ordered timing; thread wakes on fill done, redirect, disable or halt | A thread sleeps only while a fill is in progress, and always wakes
| L0 miss handler (repeated misses) | 8 threads | Per-thread consecutive-miss counters and bid mask | A thread with 31 consecutive misses gets exclusive access for its core until it hits

| L0 miss handler (retry windows) | Prefetcher and waking threads | 8-cycle prefetch pause after each fill done; prefetch blocked after an unattended miss until the next fill done, then until a core request or 16 cycles | Waking threads get the first chance at the freed miss handler, and prefetching is never blocked for good
| L1 I-cache miss port | 2 L0 micro-caches | Round-robin arbiter | Each L0 micro-cache waits for at most one miss of the other
| Decoders and ID issue slot | 2 threads of a core | Alternating decode selection and round-robin thread scheduler, per-thread FIFOs and stalls | Each eligible thread issues at least every other cycle
|===

The mechanisms in the first two rows are described with the hardware that implements them: the 2:1 LRU arbiter of the core fetch port in <<sec-ch2-fe-pipeline>>, and the 8:1 LRU arbiter with its deferred priority update in <<sec-ch3-fe-ic-arb>>. The code prefetcher and the two timed windows that hold it behind every thread are described in <<sec-ch3-l0-prefetch>>, the round-robin arbiter between the two micro-caches in <<sec-ch3-l1-arb>>, and the decoders, instruction FIFOs and thread scheduler in <<sec-ch2-fe-decode>> and <<sec-ch2-fe-sched>>. What remains, and what the rest of this section describes, is the one shared resource with no arbitration of its own: the miss handler of the L0 micro-cache.

[[sec-ch3-ll-mh]]
===== The L0 Miss Handler

The miss handler is described in full in <<sec-ch3-l0-miss>>. Enough of it is repeated here for this section to stand on its own.

Each L0 micro-cache has one miss handler: the logic that handles the L0 micro-cache's single outstanding request to the L1 instruction cache. It consists of the following:

. a three-state machine (`f0_miss_state`: Ready, Request, Fill_Wait),
. a register holding the physical address of the missing line (`f0_miss_addr`), and
. a flag indicating the miss as a prefetch miss (`f0_miss_is_prefetch`).

A miss is accepted only in the Ready state. The handler then sends the request to the L1 instruction cache (Request state), waits for the line (Fill_Wait state), writes it into the L0 micro-cache unless it is a prefetch, and returns to the Ready state, at which point fill done is generated.

Behind it, the L1 instruction cache is also single-transaction. It accepts one request, closes its request port until that request's response, and always answers with the block: on an L1 hit from its data RAM, on an L1 miss once the line has come back from the Shire Cache. A micro-cache miss that reaches the L1 therefore occupies the L1 for its whole duration, which on an L1 miss is a full round trip out of the Neighborhood.

The code prefetcher shares this same handler. It never delays a fetch in the same cycle, because a prefetch request enters the L0 pipeline only in cycles with no core request, but after a prefetch takes the handler, the prefetcher holds the handler exactly as a demand miss does (<<sec-ch3-l0-prefetch>>).

A lookup that does not hit returns a miss response to the thread in one of the following three cases:

. The line is not present in the L0 micro-cache and the handler is idle, so the handler accepts the miss and sends it to the L1 instruction cache.
. The line is not present in the L0 micro-cache but the handler is busy with another miss, so the miss is not recorded and no request is sent to the L1 instruction cache for it.
. The address misses in the L0 TLB, so a translation is requested from the page-table walker (<<sec-ch3-ptw>>) and no request is sent to the L1 instruction cache for it.

In all three cases the thread enters the sleep state (`f0_miss_pending`) and no request is issued. In the second and third cases nothing is requested for that thread, and it is the second that this section is about.

[[sec-ch3-ll-sleep]]
===== Sleep and Wake-Up

The L0 micro-cache pulses `f6_icache_fill_done` to all its threads whenever an L1 fill completes, whether it is a demand miss or a prefetch, and whenever a translation fill completes. On seeing the fill done every sleeping thread wakes and retries according to the arbitration priority. A thread whose line is now present hits, including any thread that missed on the line already being fetched, and a thread whose line is still absent misses again; if the handler is now idle, its miss is sent to the L1 instruction cache.

A thread sleeps because its own response was a miss; that is the only thing that puts it to sleep. What decides when it is woken is the task of the miss handler at that moment: the thread's own miss, the fill of another thread that keeps the handler busy, or a translation. In all three a fill is in progress, so every sleeping thread is woken when it receives the fill-done signal. The fill-done timing (<<sec-ch2-fe-miss>>) makes sure that no wake-up is lost: fill done is issued one cycle after the last response the fill can affect, and it is registered again in the Front End. A redirect, a thread disable or a pending halt clears the sleep state of the affected thread only; fill done is the only event that wakes all sleeping threads.

Which thread is served in a round is decided in F2. That is the stage where the tag is compared, where a miss is therefore first indicated, and where the handler accepts it and flops its state so that the request to the L1 instruction cache goes out in F3 (<<tab-ch3-l0-stages>>). A lookup that reaches F2 any later in the round finds the handler no longer Ready.

Two properties of this protocol follow, and they set up the rest of the section. Because the handler accepts a miss only while it is Ready, and because it is Ready only between one fill completing and the next miss being accepted, each fill-done round serves exactly one new miss. And because the whole set of sleeping threads is woken at once, the thread that is served in a round is whichever one reaches F2 first with a miss.

[[sec-ch3-ll-scenario]]
===== How a Thread Can Be Left Behind

The thread that reaches F2 first is not always the thread that waited longest. A thread that was woken by something other than fill done is already moving while the others are still asleep, and it keeps that head start all the way down the pipeline.

The following sequence is built from ordinary events and needs no fault, no error and no unusual configuration.

*Starting point.* Each fetch returns a 32-byte block, half an L0 line, and a thread buffer holds two of them (<<sec-ch2-fe-tb>>). Thread A has the first half of line X in its buffer and executes from it. It requests the second half of X. While A executes from the first half, a fill for another thread selects X as its LRU victim and evicts it, so A's request misses. The miss handler is busy with that other fill, so A's miss is *not recorded*. A receives a miss response and sleeps.

*The redirect.* While A sleeps, the integer pipeline resolves a branch in the instructions A already consumed and redirects it. The redirect clears A's sleep bit at once, and A presents a request for the branch target without waiting for any fill.

*The capture.* A's new request is in F1 when `icache_fill_done` arrives for the other thread's line. The seven other threads wake on that pulse, but they are a cycle behind: they must be granted before they enter F0, while A is already one stage inside the pipeline. A reaches F2 first, misses on the branch target, finds the handler just returned to `Ready`, and takes it.

*The others.* Each of the seven woken threads reaches F2 one or more cycles later and finds the handler in `Request` or `Fill_Wait`. Every one of their misses is discarded. They receive miss responses, sleep again, and because a miss response does not update the arbitration priority, the next round begins in exactly the same order as this one.

No part of the design is at fault: the arbiter grants A on merit, and the miss handler accepts its miss on merit. The point is that a redirect let A bypass the queue of sleeping threads entirely, and that one fill-done round can serve only one miss. A thread that is redirected often enough, or a prefetch engine that is already in the pipeline when the threads wake, can take that single opportunity repeatedly.

The result is a thread that is granted in every round, answered in every round, and never once has a line fetched on its behalf. Its arbitration priority does not change, because priority is only updated on a hit or a fault, so the arbiter cannot lift it out of the position it is in. Raising its priority would not be enough in any case: priority decides who enters the pipeline first, and the thread that enters first is not necessarily the thread that finds the handler idle.

This is the case the miss-count guard exists for.

[[sec-ch3-ll-guard]]
===== Miss-Count Livelock Guard

The Neighborhood counts, for each thread, the number of consecutive miss responses to that thread's own requests (`th_miss_cnt`, 5 bits, saturating at 31). The counter advances only when that thread's own response returns, so a thread that is not being granted does not accumulate.

While no counter is saturated, every thread may bid. When one or more saturate, a mask register (`th_miss_mask`) allows only the two threads of one Minion: the lowest-numbered Minion that has a saturated thread. Both of its threads are allowed, because the Minion holds one request at a time and the sibling's request may have to be accepted before the starving thread's can be presented at all. The mask is recomputed one cycle after every response.

The mask does not discard anything. A bid is the thread's request-register valid qualified with the mask, so masking only removes the thread's valid at the arbiter: the request itself stays in its register, untouched, and bids again in the cycle the mask is released. Nothing is re-issued and no state is lost.

With every other Minion masked, only the selected Minion's misses can reach the handler, so the starving thread's line is fetched and cannot be displaced before the thread retries. The thread then hits, which clears its counter, and the mask passes to the next Minion with a saturated thread or is removed if there is none. The mask is released by a hit, and only by a hit.

<<fig-ch3-td-l0-mask>> shows the guard at work, with the waits between rounds compressed into breaks. Every miss costs M0, TH0 a full round: the miss response puts it to sleep, fill done wakes it, it requests again and is granted, and its next response arrives four cycles after that grant.

The first response shown takes the counter to 31. The counter is loaded at the end of that cycle, so `th_miss_cnt_sat` only reads one in the next, and `th_miss_mask_en` is a registered copy of the counter enable, so the mask itself changes one cycle after that: the restrictive mask is in force two cycles after the response that saturated the counter. From that point only the two threads of Minion 0 bid.

Being alone does not give M0, TH0 its line, it gives it the miss handler. On the next round its lookup is the only one to reach F2, so its miss is accepted: `f0_l1_miss_req_valid` is driven in F3 and `f0_l1_miss_req` carries that thread's line address out to the L1 instruction cache. The response in F4 is still a miss and the thread sleeps again; the counter holds at 31 because it saturates. Only when that fill completes and the thread retries does it hit, and that hit clears the counter and releases the mask.

====== Counters and Error Responses

A response updates the counters of more threads than the one it belongs to. <<tab-ch3-miss-cnt>> lists the cases.

[[tab-ch3-miss-cnt]]
.Effect of a response on the per-thread miss counters
[cols="3,2,2",options="header"]
|===
| Response returned in F4 | Counter of the thread it belongs to | Counters of the other seven threads

| Hit | Cleared | Unchanged
| Miss, no fault or error | Incremented, saturating at 31 | Unchanged
| Page fault or access fault | Cleared | Cleared
| Bus error or ECC error | Cleared | Cleared
|===

The first two rows are the counter doing its job. The last two are deliberate: an error clears every thread's counter, not only the counter of the thread that received it.

The reason is a corner case in which a core would otherwise hang on a faulting address. A faulting thread never hits on that address, so its counter would saturate and it would hold exclusive access, which is only ever released by a hit. Clearing the counters and the mask lets the fault be delivered and handled normally rather than leaving a mask in place based on stale counts. If the fetch pattern that caused the pressure persists, the counters saturate again and the guard is triggered again.

The cost of clearing all eight is stated in <<sec-ch3-ll-assumptions>>: a sustained stream of faulting fetches from any thread defers the guard for all of them.

[[sec-ch3-ll-assumptions]]
===== Assumptions

These mechanisms guarantee forward progress in the fetch path under the following conditions:

* Every L1 miss request eventually returns a fill, and every translation request eventually completes.
* Software does not keep a thread's exclusive mode, `WFI` or other architectural stalls asserted indefinitely. These deliberately stop the affected thread and are not starvation.
* Error responses are not sustained. Because an error clears every thread's miss counter, a continuous stream of faulting fetches from other threads would defer the livelock guard. In practice each fault redirects the faulting thread to its trap handler, so such a stream does not persist.

[[sec-ch3-fe-ic-limits]]
==== Known Limitations

The properties below follow from the design of the interface. They are not defects, but they constrain how the interface may be changed and how it behaves under load.

* *Response carries no thread identifier.* A core matches a response to its request by counting cycles, so the fixed response latency is part of the interface contract. A change to the depth of the L0 pipeline has to be matched in the Front End.
* *Fill done carries no address.* Every fill wakes every sleeping thread of the micro-cache. Threads waiting for a different line arbitrate, miss again and sleep again, which costs L0 bandwidth on every fill and grows with the number of threads waiting on different lines.
* *One outstanding miss per L0 micro-cache.* A miss that arrives while the miss handler is busy is answered with a miss response but is not recorded, so its line is not requested. That thread makes progress only after an unrelated fill wakes it and it retries.
* *Starving Minions are served in a fixed order.* When several Minions have a saturated thread, the mask always selects the lowest-numbered one first. Its waiting time is bounded, because each exclusive period ends when the selected thread hits, but the order is not fair.
* *The L1 instruction cache is blocking.* It accepts one request at a time and holds its request port closed until that request's own response, which on an L1 miss waits for the line to come back from the Shire Cache. The round-robin bound of one transaction of the other micro-cache is therefore correct as a count but stands for a full round trip out of the Neighborhood, during which the other micro-cache cannot even begin a lookup that might have hit.

[[sec-ch3-l0]]
=== L0 Micro-Cache

[[sec-ch3-l0-overview]]
==== Overview

The L0 micro-cache (`icache_micro_cache`) is the first level of the Neighborhood's shared instruction cache: a fully associative, physically tagged cache of 16 lines of 64 bytes, 1 KB in all. Each Neighborhood has two instances, each shared by four Minions, eight threads: the north micro-cache serves Minions 0 to 3 and the south micro-cache serves Minions 4 to 7. The cache is split in two so that each instance is next to the Minions it serves, which reduces congestion in the Neighborhood channel. The two instances are identical except for the code prefetcher, which loads code into the L1 instruction cache at the request of software and is active only in the north micro-cache.

The micro-cache has a single request port, so the eight threads of an instance are arbitrated in the Neighborhood by an 8:1 LRU arbiter (<<sec-ch3-fe-ic-arb>>), which presents the virtual fetch address of one request per cycle. The micro-cache translates the address with its own instruction TLB and, on a hit, returns a 32-byte instruction block, half a line. On a miss it requests the complete 64-byte line from the L1 instruction cache, the next level, which both micro-caches share.

The design rests on four decisions:

. *Never stalls, fixed latency:* a miss does not block the requests behind it, so the cache accepts one request in every cycle, serves hits while a miss is outstanding, and returns a response for every request, hit or miss, four cycles after the grant. The Front End depends on the fixed latency, because it recognizes its responses by timing alone (<<sec-ch2-fe-track>>).
. *Translate, then look up:* the tags are physical, so the instruction TLB translates the fetch address in the cycle after the request is accepted, and the physical tag is compared with all 16 lines in the next cycle.
. *One fill at a time:* one line request to the L1 instruction cache and one page-table walk can be outstanding. A miss that finds the resource it needs busy is answered but not recorded, and every completed fill wakes all sleeping threads (<<sec-ch3-fe-ic-miss>>).
. *One TLB for four Minions:* each Minion owns four of the 16 TLB entries, except in cooperative mode, a Shire-wide setting held in the `shire_coop_mode` ESR, in which the four Minions share all 16 entries.

| Allocation | A line is allocated only for a core miss accepted by the miss handler. Prefetch and bypassed fills are not allocated.
| Write policy | Read-only. Lines are written only by fills and by APB debug writes, and nothing is written back.
| Coherence | None. The micro-cache does not snoop. A change to code in memory is seen only after a flush (<<sec-ch3-l0-flush>>).
|===

[[sec-ch3-l0-addr]]
===== Address Decode

The micro-cache receives a 49-bit fetch address, the 48-bit virtual address and its extension bit, and generates a 40-bit physical address (<<fig-ch3-l0-addr>>). With 4 KB pages the low 12 bits, the page offset, pass through unchanged. The virtual page number, bits 47:12, goes to the instruction TLB with the extension bit, and the TLB returns a 28-bit physical page number (<<sec-ch3-l0-tlb>>). The micro-cache divides the physical address into three fields: bits 39:6 are the 34-bit tag, compared with the tags of all 16 lines; bit 5 selects the 32-byte half of the line that is returned; and bits 4:0 are not used by the micro-cache, because the Front End extracts the instruction from the block (<<sec-ch2-fe-extract>>).

[[sec-ch3-l0-pipeline]]
==== Pipeline Stages

This section describes the five L0 micro-cache stages, F0 to F4, and the fill-done stage F5. A lookup runs from F0 to F4: a request enters in F0, is translated by the instruction TLB in F1, is compared with the tags and checked by the PMA unit in F2, reads the data array in F3, and returns its response in F4. A miss accepted in F2 sends its line request to the L1 instruction cache in F3. The fill runs independently of the lookup, and fill done is driven in F5, three cycles after the fill finishes.

<<fig-ch3-l0-top>> shows the north micro-cache, the instance that contains the prefetcher, with each block drawn in the stage in which it operates. Blocks outside the frame are its neighbors: the cores, the per-thread request registers and the 8:1 LRU arbiter of the Neighborhood, the page-table walker, the L1 instruction cache, and the ESR and APB interfaces.

[[fig-ch3-l0-top]]
.L0 micro-cache detailed pipeline diagram
image::ch03/fig-l0-detailed-pipeline.drawio.png["L0 micro-cache detailed pipeline diagram",width=80%,align=center]

F0 Stage:: The F0 stage arbitrates between the core request granted by the 8:1 LRU arbiter and a request from the code prefetcher, and always gives priority to the core request. In a cycle with no core request, the code prefetcher can enter its request, if it is in its Request state and no miss unattended by the miss handler is pending (<<sec-ch3-l0-pf-window>>). A prefetch request uses the same path through the pipeline as a core request, so a prefetch flag goes with each request to the next stages to tell the two apart. The request, the identifier of its Minion, the bypass bit and the prefetch flag are registered into F1.
F1 Stage:: The F1 stage translates the virtual address of the request to a physical address in the instruction TLB. The translation uses the supervisor and machine address-translation registers that each Minion sends to the micro-cache (`satp_info` and `matp_info`), and the privilege level of the fetch selects one of the two (<<sec-ch3-l0-tlb-lookup>>). The TLB returns the physical page number, a miss indication, and page and access faults. A TLB miss starts a page-table walk if no walk is in progress and the address is valid, and the walk request goes to the page-table walker one cycle later (<<sec-ch3-l0-tlb-walk>>). The request continues to F4 and receives a miss response, and the thread retries after fill done.
F2 Stage:: The F2 stage forms the physical address from the page number and the page offset. The tag is compared with all 16 lines of the micro-tag array, and with the line that a fill writes in the same cycle, while the PMA unit checks the address. The LRU state is updated on a hit, on an accepted miss, and when the L1 response writes the line into the victim entry. A line miss with no TLB miss and no fault is accepted if the miss handler is Ready: the handler records the physical address, the LRU victim and the bypass and prefetch flags, and the victim's valid bit is cleared. A miss that finds the handler busy is not recorded and receives only the miss response in F4. In bypass mode the tag is compared with the bypass register instead of the micro-tag array, and a prefetch request is forced to miss.
F3 Stage:: The F3 stage reads the micro-data array with the one-hot hit vector that the micro-tag array generates in F2, and selects the 32-byte half-line named by address bit 5; in bypass mode the half comes from the bypass register. The response is a miss when the tag misses or the TLB misses. The ECC and bus-error flags stored with the line are valid only on a hit. If F2 accepted a miss, the miss handler is in its Request state in this cycle and drives the line request to the L1 instruction cache.
F4 Stage:: The F4 stage registers the response and drives it to the four Minions, four cycles after the grant, for a hit and for a miss alike. A prefetch request produces no response.
F5 Stage:: The F5 stage drives fill done, which tells the sleeping threads that a line or translation fill is complete. Fill done is generated in F2 and passes through F3 and F4 to F5. F5 is not part of a lookup.

<<fig-ch3-l0-flow>> shows the path of one request from F0 to F4 and the fill that a miss starts. Every request leaves the pipeline at F4 with a hit, miss or fault response. The fill path on the right runs independently of the lookup and ends with fill done in F5. The time to fill a line depends on the L1 instruction cache and is given in <<sec-ch3-l1>>.

[[sec-ch3-l0-tlb]]
==== Instruction TLB

The instruction TLB translates the virtual address of a request, from a core or from the code prefetcher, to a physical address in F1. It is `icache_tlb_array`, a wrapper around `tlb_top`. The data cache of each Minion has its own instance of the same `tlb_top` (`dcache_tlb_array`), so the two caches share the design of the TLB but not its translations. Each wrapper only adapts `tlb_top` to its cache. The instruction wrapper sets 16 entries for four Minions, marks every request as an instruction fetch, and registers the address-translation registers of the four Minions (`satp_info` and `matp_info`) and `esr_vmspagesize`; `tlb_top` registers `esr_shire_coop_mode`. A change to any of these settings takes effect one cycle later.

A TLB miss needs a page-table walk, and the TLB has at most one walk outstanding (<<sec-ch3-l0-tlb-walk>>). The TLB does not block during a walk: it continues to look up every request, and a request that hits receives its translation. A request that misses during a walk starts no walk and receives a miss response with no data, and its thread retries after fill done.

<<tab-ch3-l0-tlb-if>> lists the interface of `icache_tlb_array`, grouped by the block at the other end. The request and the response connect to F1 of the micro-cache pipeline: the TLB answers in the same cycle, and the micro-cache registers the response into F2. The configuration inputs, the invalidation pulses and the walker ports pass through to ports of the micro-cache (<<tab-ch3-l0-ports>>).

[[sec-ch3-l0-tlb-org]]
===== Organization

The TLB has 16 entries, and all of them hold translations of one page size, 4 KB, 2 MB or 1 GB, set by `esr_vmspagesize`. <<fig-ch3-l0-tlb-org>> shows the format of an entry and how the 16 entries are divided between the Minions. An entry holds 70 bits in a latch-based register file: the 34-bit tag, the 28-bit physical page number, the `x`, `w`, `r`, `u`, `a` and `d` bits of the page-table entry, the access-fault flag of the walk, and the execution mode of the walk. The valid bits are separate flip-flops. The tag field is 34 bits because that is the longest tag, the one of 4 KB pages in per-Minion mode; cooperative mode and larger pages use fewer bits and store them with zero bits (<<tab-ch3-l0-tlb-fields>>).

A walk can end without a translation. The walker returns the last page-table entry that it reads, and that entry is not a valid leaf when `v` is clear, when `r` and `x` are both clear, or when `w` is set and `r` is clear, a reserved encoding. A walk that ends in an access fault gives no translation either. The TLB still writes the entry, with `x`, `w` and `r` as 0. The thread's retry then hits that entry and takes a page fault, and also an access fault if the walk ended in one, instead of starting the same walk again.

[[fig-ch3-l0-tlb-org]]
.Instruction TLB organization
image::ch03/fig-l0-tlb-org.drawio.png["Instruction TLB organization",width=100%,align=center]

The TLB is direct-mapped in both of its modes: the index selects one entry, and a translation is either in that entry or not in the TLB. The mode, set by `esr_shire_coop_mode`, decides where the index comes from:

* *Per-Minion mode:* the micro-cache serves four Minions, so the 16 entries are divided into four groups of four, one group for each Minion. The upper two index bits are the Minion identifier, and the lower two come from the virtual page number. A Minion replaces only its own entries, so a Minion that touches many pages cannot evict the translations of the other three.
* *Cooperative mode:* all 16 entries are shared, and all four index bits come from the virtual page number. An entry carries no Minion identifier, so an entry filled for one Minion hits for the other three. Cooperative mode therefore assumes that the four Minions use the same translation, and in return the group has 16 entries instead of four for each Minion.

<<fig-ch3-l0-tlb-index>> shows how the index and the tag are taken from the virtual page number for 4 KB pages, and <<tab-ch3-l0-tlb-fields>> lists them for all page sizes. Each stored tag is written most-significant field first. Cooperative mode adds two zero bits at the top, because its index takes two more address bits; a 2 MB or 1 GB page adds 9 or 18 zero bits at the bottom, one page-table level of 9 bits for each step above 4 KB.

[cols="1,2,3,4",options="header"]
|===

| 4 KB | Per-Minion | Minion identifier, VA[13:12] | {VA[47:14]} (34)

[[sec-ch3-l0-tlb-lookup]]
===== Lookup and Permission Check

<<fig-ch3-l0-tlb-lookup>> shows the lookup in F1 as a sequence of decisions from top to bottom. The canonical-address check comes first because it depends only on the mode of the selected register, not on whether translation is enabled. The privilege level of the fetch, `vm_status.prv`, selects the translation register: `matp_info` of the requesting Minion in M-mode, `satp_info` otherwise. For an instruction fetch `mprv` is ignored. Translation is enabled when the selected register is not in Bare mode and the thread is not in debug mode. When translation is disabled, the TLB returns VA[39:12] as the physical page number and never misses.

[[fig-ch3-l0-tlb-lookup]]
.Instruction TLB lookup and permission check
image::ch03/fig-l0-tlb-lookup.drawio.png["Instruction TLB lookup and permission check",width=65%,align=center]

An entry hits when it is valid, its tag matches, and its execution mode matches the fetch: an entry walked for M-mode hits only for M-mode fetches, and an entry walked for S-mode or U-mode only for those. A miss goes to the walk state machine (<<sec-ch3-l0-tlb-walk>>).

The TLB reports two faults, listed in <<tab-ch3-l0-tlb-faults>>. The page fault comes from three checks:

* *Privilege check:* in U-mode the entry must have `u` set; in S-mode and M-mode it must have `u` clear, unless `mstatus.SUM` is set.
* *Accessed bit:* the TLB does not set `a`. It raises a page fault instead, and software updates the page-table entry.
* *Canonical address:* in Sv48, VA[48] must equal VA[47]; in Sv39, VA[47:38] must also all be equal. A non-canonical address raises the page fault whether or not the entry hits, and starts no walk.

.Instruction TLB faults
[cols="2,5",options="header"]
|===
| Signal | Condition

| `xcpt_if`, instruction page fault | The entry hits and `x` is clear, the privilege check fails, or `a` is clear; or the address is not canonical. `x` is also clear when the walk finds no valid leaf entry (<<sec-ch3-l0-tlb-org>>).

A walk that ends in an access fault leaves `x` clear and AF set, so the retry reports both faults. The integer pipeline gives the access fault priority, and the thread takes an instruction access fault.

[[sec-ch3-l0-tlb-walk]]
===== Page-Table Walk

A page-table walk reads the page tables in memory, from the root table of the selected translation register down to the leaf entry that holds the translation. The TLB does not read the page tables itself: it sends the walk to the shared page-table walker (<<sec-ch3-ptw>>).

For the walk the TLB uses a three-state machine, shown in <<fig-ch3-l0-tlb-fsm>>:

* *Ready:* no walk is in progress. A TLB miss on a canonical address captures the Minion, the virtual page number and the walk request, and moves the state machine to Request. The request carries the translation mode and root page number of the selected register, the privilege level and the virtual page number (<<tab-ch3-l0-ptw-req>>).
* *Request:* sends the walk request to the walker. `ptw_req_valid` is held until the walker accepts the request with `ptw_req_ready`, and the state machine then moves to Wait. An invalidation withdraws the request and returns the state machine to Ready (<<sec-ch3-l0-tlb-inval>>).
* *Wait:* waits for the walker's response. The response is registered for one cycle, and in the next cycle the entry is written at the index of the request's Minion and virtual page number, unless the walk is cancelled. The state machine returns to Ready in the same cycle.

[[fig-ch3-l0-tlb-fsm]]
.Instruction TLB walk state machine
image::ch03/fig-l0-tlb-fsm.drawio.png["Instruction TLB walk state machine",width=70%,align=center]

A walk starts only from Ready, so one walk at most is in progress. A miss that arrives in Request or Wait receives a miss response and starts no walk. `fill_pending` is set in Request and Wait. The micro-cache detects the end of the walk as the fall of `fill_pending` and turns it into `f2_tlb_fill_done`, which reaches the cores as `f5_resp_fill_done` three cycles later.

[[sec-ch3-l0-tlb-inval]]
===== Invalidation

`tlb_invalidate` carries one pulse per Minion, driven when the Minion writes 1 to bit 1 of its `cacheInvalidate` CSR (0x7D0). Outside cooperative mode a pulse clears the four entries of that Minion; in cooperative mode any pulse clears all 16. A walk in progress for the invalidated Minion, or any walk in cooperative mode, is cancelled: in Request it is withdrawn, and in Wait its response is discarded. The invalidation is held until the outstanding walk ends, so a response from before the invalidation can never be written. The OR of the four pulses, registered once, is forwarded to the walker on `ptw_invalidate`.

The entries carry no address-space identifier, and a change of `satp_info` or `matp_info` does not invalidate them. Software must invalidate the TLB through `cacheInvalidate` after it changes the translation.

[[sec-ch3-l0-tlb-pages]]
===== Page Size

`esr_vmspagesize` selects 4 KB, 2 MB or 1 GB for every entry, and moves the index and the tag accordingly (<<tab-ch3-l0-tlb-fields>>). A change of `esr_vmspagesize` does not invalidate the entries either. The walker ends the walk at the page-table level of that size. A leaf found at a higher level is split into pages of the configured size, with the walker supplying the lower page-number bits from the virtual address. For a configured size of 2 MB or 1 GB the walker returns the page-number bits below that size as zero, and the micro-cache forms the physical address from the returned page number and VA[11:0] only.

[[sec-ch3-l0-tags-data]]
==== Micro-Tag and Micro-Data Arrays

The micro-tag array and the micro-data array hold the 16 lines of the micro-cache, and the LRU selector chooses the line that a new miss replaces. The micro-tag array works in F2: it holds the physical tag of each line, and compares the tag of the request, translated by the instruction TLB in F1, with all 16 tags at once. The micro-data array works in F3: it holds the lines, and returns the 32-byte half that the request needs. The two arrays have the same 16 entries, so the entry that holds a tag also holds its line, and one one-hot vector selects both. <<fig-ch3-l0-uarray>> shows the format of an entry of each array, and how a lookup passes from one array to the other.

[[fig-ch3-l0-uarray]]
.Micro-tag and micro-data arrays
image::ch03/fig-l0-uarray-org.drawio.png["Micro-tag and micro-data arrays",width=100%,align=center]

[[sec-ch3-l0-tag-array]]
===== Micro-Tag Array

The micro-tag array holds 16 tags, one for each line. It has no index: the cache is fully associative, so a line can be in any entry. Each tag is the line address, PA[39:6], 34 bits, stored in a latch-based register file that reads all 16 entries at once (`rf_latch_1r_1w_par`). Each entry also has a valid bit in a flip-flop beside the register file. <<tab-ch3-l0-tag-ports>> lists the ports of the array.

[[tab-ch3-l0-tag-ports]]
.Micro-tag array ports
[cols="2,1,6",options="header"]
|===
| Port | Stage | Function

| Read | F2 | Receives PA[39:6] of the request and returns the one-hot hit vector.
| Victim | F2 | Receives the LRU victim of an accepted miss and clears its valid bit.
| Write | Fill cycle | Writes the tag that the miss handler recorded into the victim entry, and sets its valid bit. APB debug writes share the port, and the fill has priority.
| Flush | F0 | `f0_flush_data` clears all valid bits (<<sec-ch3-l0-flush>>).
| APB | – | Reads and writes the tag and the valid bit of one entry (<<sec-ch3-l0-dbg>>).
|===

*Lookup.* In F2 the array compares the tag of the request with all 16 tags in parallel. An entry hits when it is valid, its tag equals PA[39:6], it receives no write in this cycle, and no flush is in progress. A line is allocated only after a miss, so at most one entry hits, and the result is a one-hot hit vector of 16 bits. The vector goes to two places in the same cycle: to the LRU selector, which records the entry as the most recent, and through the stage register to the micro-data array, which reads the line with it in F3.

*Lookup in the fill cycle.* While a fill writes a tag, the array also compares the request with the tag that is written. The entry under write cannot hit on its old tag, but a request whose tag matches the new tag hits on that entry. A request that arrives in the fill cycle therefore sees the new line and does not miss on it (<<fig-ch3-l0-fill>>).

*Miss.* When no entry hits and the miss handler accepts the miss, the array frees the victim that the LRU selector chooses: it clears the valid bit of the victim in F2, so the entry cannot hit while its new line is outstanding. The miss handler records the victim and the tag, and requests the line from the L1 instruction cache in F3 (<<sec-ch3-l0-mh>>). A bypassed or prefetch miss frees no victim, because its fill writes no array.

*Fill.* When the L1 instruction cache returns the line for the outstanding miss request, the array writes the tag that the miss handler recorded into the victim entry, and sets the valid bit (<<sec-ch3-l0-fill-write>>).

The valid bits change on four events:

* *Accepted miss:* the valid bit of the victim is cleared.
* *Fill:* the valid bit of the victim is set, unless a flush arrived while the fill was outstanding.
* *Flush:* all valid bits are cleared.
* *Debug write:* the valid bit is written with the tag.

[[sec-ch3-l0-data-array]]
===== Micro-Data Array

The micro-data array holds the 16 lines, entry for entry with the micro-tag array. Each entry is 514 bits in a latch-based register file with one-hot read and write selects (`rf_latch_1r_1w_dec`): the 512-bit line, the ECC-error flag (bit 512) and the bus-error flag (bit 513) that the L1 instruction cache delivers with the line. <<tab-ch3-l0-data-ports>> lists the ports of the array.

[[tab-ch3-l0-data-ports]]
.Micro-data array ports
[cols="2,1,6",options="header"]
|===
| Port | Stage | Function

| Read | F3 | Receives the one-hot hit vector from F2 and returns the selected entry. APB debug reads share the port and wait for a cycle with no request in F3.
| Write | Fill cycle | Writes the line and its error flags into the victim entry. APB debug writes share the port, and the fill has priority.
| APB | – | Reads and writes one entry (<<sec-ch3-l0-dbg>>).
|===

*Read.* In F3 the array reads the entry that the hit vector selects, and PA[5] selects the 32-byte half that goes to the response in F4. On a miss the hit vector is all zeros, and the response carries no instruction block. The error flags go to the response with the block, and they are valid only on a hit.

*Write.* The fill writes the line and its error flags into the victim entry, in the same cycle as the tag (<<sec-ch3-l0-fill-write>>).

[[sec-ch3-l0-lru]]
===== LRU Selector

The LRU selector (`lru_sel`) decides which line a new miss replaces. It keeps the exact order of use of all 16 entries, and the victim is always the entry that was used least recently. For each pair of entries the selector holds one bit that tells which of the two was used more recently. An entry is the victim when it is older than each of the other 15, and the selector presents the victim as a one-hot vector, in every cycle, to the micro-tag array and the miss handler.

Three events in F2 count as a use, and each makes the entry the most recent one:

* *Hit:* the entry that hits.
* *Accepted miss:* the victim, when the miss handler takes the miss.
* *Line fill:* the victim again, when its line is written. While the line was outstanding, other entries continued to hit and became more recent, so without this second update the new line could be the next victim as soon as it arrives.

The selector is not updated for a prefetch request or a bypassed request, because neither keeps a line in the arrays. The selector also ignores the valid bits, so it does not look for an empty entry first. Empty entries exist only after reset or a flush, and after reset the selector hands the entries out in order, entry 0 first.

[[sec-ch3-l0-fill-write]]
===== Fill Write

A line from the L1 instruction cache is written into the tag and data arrays in the cycle `f0_l1_miss_resp_valid` is asserted, at the victim recorded when the miss was accepted. The latch-based register files need their write enable one cycle ahead of the write, and `f0_l1_miss_resp_early_valid` supplies it; the L1 derives it from the next-cycle value of its response valid. Prefetch and bypassed fills write neither array.

<<fig-ch3-l0-fill>> shows the write in cycle 3. All the requests in the figure are for the same line, line A: the outstanding miss in `f0_miss_addr`, which the L1 instruction cache answers in cycle 3, and the lookups of M1, TH0 and M2, TH0. M1, TH0 reaches F2 in cycle 2, before the write, and misses; the miss handler is still in Fill_Wait, so nothing is recorded for it. M2, TH0 reaches F2 in cycle 3, the write cycle, and hits on the line being written. Their responses leave F4 in cycles 4 and 5, the handler returns to Ready in cycle 4, and fill done is driven in cycle 6, three cycles after the write.

==== PMA Check

The PMA unit (`icache_pma_unit`) checks the physical address in F2 against the regions from which instructions may be fetched, and reports an access fault and whether the address is cacheable. <<tab-ch3-l0-pma>> lists the regions, decoded from the address-map defines in `shire_defines.vh`. [[sec-ch3-l0-miss]]
==== Miss Handling

[[sec-ch3-l0-mh]]
===== Miss Handler

The miss handler fetches missing lines from the L1 instruction cache. It sends the line request, and it keeps the information about the miss that the fill needs when the line comes back. It serves three kinds of miss: a core request that misses in the micro-tag array, a bypassed core request that misses in the bypass register, and a prefetch request. A TLB miss never reaches the miss handler. Without a translation there is no physical address to send to the L1, so the walk state machine of the instruction TLB handles the TLB miss instead (<<sec-ch3-l0-tlb-miss>>).

The miss handler holds one line request at a time and uses a three-state machine, shown in <<fig-ch3-l0-miss-fsm>>:

* *Ready:* no line request is outstanding, and the handler can take a miss. It takes one in F2, asserts `f2_miss` and moves to Request, when the request in F2 is valid, does not hit, has a translation, and has no page fault or access fault.
* *Request:* drives the line request on `f0_l1_miss_req_valid` with the physical address, and holds it until the holding register of the instance in `icache_top` takes it (`f0_l1_miss_req_ready`). The handler then moves to Fill_Wait.
* *Fill_Wait:* waits for the line. The line is written in the cycle `f0_l1_miss_resp_valid` arrives, and the handler is back in Ready in the next cycle.

A miss that arrives while the handler is in Request or Fill_Wait still receives its miss response, but nothing is recorded for it (<<sec-ch3-l0-tag-miss>>).

[[fig-ch3-l0-miss-fsm]]
.Miss handler state machine
image::ch03/fig-l0-miss-fsm.drawio.png["Miss handler state machine",width=70%,align=center]

The response from the L1 instruction cache carries the line and its two error flags, but not its address. So when the handler takes a miss, it records everything the fill needs later:

* *Tag:* PA[39:6] of the miss, in `f0_miss_addr`. It is the address of the line request, and the tag that the fill writes into the micro-tag array or into the bypass register.
* *Victim:* the one-hot entry that the LRU selector chose, in `f0_miss_victim`. The fill writes the tag and the line into this entry.
* *Flags:* bypassed, prefetch, and L0 write disabled, the last set for a bypassed or prefetch request. They decide where the line goes: into the arrays, into the bypass register, or nowhere in the micro-cache.

[[sec-ch3-l0-tag-miss]]
===== Line Miss

A request that translates but does not hit receives a miss response. If the handler is in Ready, the miss is accepted and the line is requested; if it is busy, nothing is recorded, and the thread fetches the line after a later fill done, when it retries and finds the handler idle. A core miss that is not recorded also opens the window in which the code prefetcher holds back (<<sec-ch3-l0-pf-window>>). <<fig-ch3-l0-tx-miss>> shows a line miss that finds the miss handler in Ready, and <<fig-ch3-l0-tx-busy>> one that finds it busy. <<tab-ch3-l0-tx-miss>> lists the steps of both side by side. [[sec-ch3-l0-flush]]
==== Flush

`f0_flush_data` invalidates the micro-cache. `neigh_shared_icache` forms it as the OR of the flush requests of the eight Minions, registered once, and drives it to both micro-caches and to the L1 instruction cache. In the flush cycle the valid bits of all micro-tag entries are cleared, and no lookup hits. A fill outstanding at the flush is written when it arrives but left invalid, because the flush is remembered until the miss handler returns to Ready. The flush does not affect the TLB or the bypass register; TLB entries are invalidated through `tlb_invalidate` (<<sec-ch3-l0-tlb-inval>>).

[[sec-ch3-l0-bypass]]
==== Bypass Mode

Bypass mode is intended to bypass both levels of the instruction cache, so that no line is kept. It is set by the `bypass_icache` chicken bit of the Neighborhood, received as `esr_bypass_icache`. The L1 instruction cache then never hits and never allocates, and every line comes from the Shire Cache through the L1.

The micro-cache cannot bypass itself in the same way. Its response latency is fixed at four cycles after the grant, and the Front End depends on that latency (<<sec-ch2-fe-track>>), but a line from the Shire Cache takes much longer. A bypassed request therefore still passes the complete micro-cache pipeline and receives a miss response, and its thread retries after fill done. For the retry to hit, the micro-cache keeps the last bypassed line in a one-line bypass register. <<fig-ch3-l0-bypass-reg>> shows its format: the tag, the 512-bit line, the two error flags and a valid bit, all in flip-flops.

* *Sampling:* the bit is registered with each request in F0 and travels with it; it is recorded by the miss handler when the miss is accepted.
* *Lookup:* in F2 a bypassed request compares its tag with the bypass register instead of the micro-tag array. The register does not hit in the cycle it is loaded.
* *Fill:* the fill of a bypassed core miss loads the bypass register; the arrays and the LRU state are not touched (<<tab-ch3-l0-tx-bypfill>>).
* *Read:* in F3 the 32-byte half and the error flags come from the bypass register.
* *Exit:* the register is invalidated when a request that is not bypassed passes F2.

[[sec-ch3-l0-prefetch]]
==== Code Prefetcher

The code prefetcher loads a range of consecutive lines into the L1 instruction cache, so that code is resident before the cores execute it. It is built into the north micro-cache so that its requests use the micro-cache's TLB and PMA check. Its requests pass through the micro-cache pipeline but never allocate in the L0: they are forced to miss, write no array and produce no response. Only the L1 keeps the line.

[[sec-ch3-l0-pf-start]]
===== Starting an Operation

Software starts an operation by writing the start line address (42 bits, VA[47:6]) and the line count to one of three Shire ESRs: `icache_uprefetch`, `icache_sprefetch` or `icache_mprefetch`. The ESR written sets the privilege of the operation. A write is accepted only in cooperative mode. Pending requests are served in privilege order: an M-mode request at once, and an S-mode or U-mode request only when no operation is in progress or the current operation has the same or lower privilege. The served request reaches the north micro-cache as `esr_prefetch_conf` and a pulse on `esr_prefetch_start`.

A start pulse moves the prefetcher to Request from any state. An operation in progress is abandoned and the new one starts at once. Prefetch requests carry Minion identifier 0 and the privilege of the operation, with the other virtual-memory status fields clear; the RTL comment gives the reason as the virtual-memory configuration being the same for all Minions.

Advancing adds one to the line address and subtracts one from the line count. An address that overflows bit 47 changes bit 48, which the TLB reports as a non-canonical address when translation is in Sv39 or Sv48 mode. The pause after every fill done leaves the freshly woken threads a window in which to retry before the prefetcher takes the miss handler again.

<<fig-ch3-l0-tx-pf>> shows one prefetch request, and <<tab-ch3-l0-tx-pf>> lists its steps. The request is forced to miss, so it always takes the miss handler if the handler is in Ready, and it produces no response. <<fig-ch3-l0-tx-pffill>> shows its fill.

[[sec-ch3-l0-pf-window]]
===== Unattended-Miss Window

When a core lookup misses and the miss is not accepted, the thread retries after the next fill done. The unattended-miss state machine holds the prefetcher back until that retry can enter the pipeline: a prefetch request is qualified (`f0_prefetch_req_valid`) only while the state machine is in NotPending.

* *NotPending to FillDone_Wait:* a core request in F2 misses and no miss is accepted for it.
* *FillDone_Wait to Req_Wait:* `f5_resp_fill_done`.
* *Req_Wait to NotPending:* a core request enters F0, or 16 cycles pass.

[[sec-ch3-l0-pf-done]]
===== Completion

`esr_prefetch_done` resets high, is set by a start pulse, is cleared when the prefetcher enters Request, and is set again when the fill of the last line returns. It is returned to the Shire ESR block.

[[sec-ch3-l0-dbg]]
==== Debug Access

The micro-tag and micro-data arrays of both instances can be read and written over APB. `icache_top` decodes the upper bits of its 10-bit APB address and passes the low eight bits to the selected instance (<<tab-ch3-l0-dbg-map>>).

[[tab-ch3-l0-dbg-map]]
.Micro-cache debug address
[cols="1,5",options="header"]
|===
| Bits | Use

| 9 | 1: micro-cache space. 0 selects the L1 tag array.
| 8 | Instance: 0 for the north micro-cache, 1 for the south.
| 7 | 0: micro-data array. 1: micro-tag array or error flags.
| 6:3 | Line number, 0 to 15.
| 2:0 | With bit 7 = 0: 64-bit word within the line. With bit 7 = 1: bit 2 selects the tag (0) or the error flags (1).
|===

* *Tag access:* a read returns the tag in bits 33:0 and the valid bit in bit 34; a write sets both from the same bits. A write waits for a cycle in which no fill writes the array.
* *Data access:* a read returns one 64-bit word of the line. A write is a read-modify-write of the whole 514-bit entry: the line is read, the selected word replaced, and the entry written back. Reads wait for cycles in which F3 does not read the array, and writes for cycles in which no fill writes it.
* *Error flags:* bit 0 is the ECC-error flag and bit 1 the bus-error flag of the line, read or written in the same way.

`apb_pslverr` is never asserted.
